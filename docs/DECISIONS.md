## ADR-004 (2026-07-16): Persona-driven adaptive-UX architecture
Context: Femio must personalize deeply across ~70 life-stage/condition scenarios while staying one coherent app and out of medical-device scope. Decision: a single Master Adaptation Model — one **constant EMR core + additive persona layers**, a wizard→persona resolver, a **Z1 "Other/Custom" nearest-persona fallback**, and a universal-events layer (positive test, loss, red-flags, mood-screen) inherited by all personas. Seven invariants govern it, headlined by **"personalize, never restrict"** (emphasis/defaults/tone/alerts change; access never does) and **"never diagnose/treat/prevent/contracept."** Alternatives: separate apps/modes per stage (fragmentation, the market's core failure); hard-coded per-persona UIs (unmaintainable at 70+). Consequences: remaining personas inherit invariants/events/data-model and only add their own fields+content+transitions; the C8→D7 (thyroid TTC→pregnancy) flow is the reference implementation. (→ 09_MASTER_ADAPTATION_MODEL.md)

## ADR-005 (2026-07-16): Keep orchestration lean — no external multi-agent platform yet
Context: Considered a "Femio Agent OS" (n8n + LangGraph + LiteLLM + Figma MCP + CI) to orchestrate research/build/test/translate across Gemini/OpenAI/Claude. Decision: **defer** it. Pro chat subscriptions (ChatGPT/Claude/Gemini) are not API access, so an orchestrator would require separate pay-per-token API accounts; and building the platform would precede building the product. Near-term: **GitHub as single source of truth**, Cowork subagents for research, per-provider coding CLIs (Claude Code/Codex/Gemini CLI) for build, GitHub Actions for deterministic tests, cross-provider PR review. Adopt n8n/LangGraph/LiteLLM only if/when manual coordination becomes the bottleneck and API spend is approved. Consequences: fast progress now, no premature infra; revisit trigger = coordination pain. (Persona research is synthetic/public — no real user health data through any research agent.)

## ADR-006 (2026-07-16): Design-token system — two-tier, CSS-canonical, AA-verified
Context: P0.11 needs a premium, maintainable design foundation that serves web now and native later, in 4 languages incl. Arabic/RTL, and encodes Femio's brand + compliance rules. Decision: a **two-tier token system** — primitives (raw 50–950 ramps) → semantic role tokens (`--primary`, `--surface`, `--danger`); components consume **only** semantic tokens; dark mode remaps the semantic layer alone. **`femio.tokens.css` is the single source of truth**, mirrored to `femio.tokens.json` (W3C format, for tooling/native/Figma import) and `femio.tailwind.preset.js` (for the Next.js app). Palette: violet #7C3AED primary (authority+warmth, not stereotype pink), raspberry accent (CTAs only), teal (health/fertile), amber (uncertainty), warm violet-tinted neutrals; Fraunces/Inter + IBM Plex Sans Arabic. Compliance encoded in tokens: predictions render via a soft/dotted `--prediction-band` (never certain), status never color-only. Alternatives: single-tier hardcoded palette (unmaintainable), Tailwind-only (no native/Figma path). Consequences: one dial per decision, guaranteed theme+a11y consistency; contrast **programmatically verified** (fixed `--text-subtle` 3.26→4.64 and added AA-safe `*-solid` fill tokens). Logo is a v1 concept (open cycle ring); full lockup set + trademark clearance carried to brand handoff / P0.12. (→ 12_BRAND_DESIGN_TOKENS.md, assets/brand/)

## ADR-007 (2026-07-16): System architecture — constant-core EMR + additive layers on Supabase, server-side resolver
Context: P1.1 must turn 73 persona specs + the adaptation model into a buildable schema for a privacy-first, i18n, one-account app. Decision: **Supabase (Postgres + RLS + auth, EU region)** behind a **Next.js 15 PWA**; data modeled as a **constant EMR core** (cycles, symptoms, meds, screeners, conditions) + **additive persona-layer tables** (labs, vitals, fertility, pregnancy, partner_links) with a persisted **`persona_state`** + append-only **`adaptation_events`**; the **adaptation resolver + predictions run server-side** (Postgres RPC / Edge Functions) so logic is centralized and health data stays in trusted infra; **owner-only RLS** on all health tables (anonymous rows device-keyed), partner access only via curated security-definer RPCs; **transition rules encoded as data** so ~73 personas plug in without bespoke code; Payload CMS authors content, Postgres serves per-locale with reviewer-sign-off gating. Alternatives: single wide table (unmaintainable), client-side resolver (leaks logic/data, unsafe), Firebase (weaker relational/RLS story). Consequences: clean build order P1.2→P1.25; privacy + i18n + medical-device guardrails enforced at the data layer. Open sub-decisions (transition-rules table vs typed config; prediction v1 model; anon→registered merge) logged as ADRs when decided. (→ 14_SYSTEM_ARCHITECTURE.md)

## ADR-008 (2026-07-23): Pin Tailwind CSS v3 to consume the existing token preset
Context: P1.2 scaffold must wire the app to the canonical design tokens. `assets/brand/tokens/femio.tailwind.preset.js` is authored in **Tailwind v3 form** (JS `module.exports`, `presets:[]`, `theme.extend`, semantic tokens mapped to `var(--…)`). Next.js 15's default scaffold now ships **Tailwind v4** (CSS-first `@theme`, no JS preset), which would not consume this preset without a full rewrite of the token bridge. Decision: **pin Tailwind v3.4** in `apps/web` and consume the preset via `presets: [femioPreset]`; expose the canonical token files as a `@femio/tokens` pnpm-workspace package (`assets/brand/tokens/package.json`) so the app imports `tokens.css` (custom properties) and `tailwind-preset` without duplicating the source of truth (ADR-006 stands: `femio.tokens.css` remains canonical). App-level `tailwind.config.ts` layers only a font-family override pointing at the self-hosted `next/font` CSS variables. Alternatives: migrate the whole token system to Tailwind v4 `@theme` now (churn + risk before any product code; revisit later), or duplicate tokens into the app (violates single-source). Consequences: tokens flow through Tailwind utilities untouched; a future Tailwind v4 migration is a self-contained follow-up. (→ apps/web/tailwind.config.ts, assets/brand/tokens/)

## ADR-009 (2026-07-23): i18n messages as local JSON now, DB translation-portal later
Context: doc 14 §7 specifies UI strings live in the DB (`ui_strings`, ICU) served to next-intl and managed by the admin translation portal (P1.19) — but P1.2 predates any database (P1.3). Decision: scaffold next-intl with **local per-locale JSON catalogs** (`apps/web/messages/{en,ar,fr,es}.json`) loaded in `src/i18n/request.ts`; keep that loader as the **single swap point** so P1.19 can replace the JSON import with a DB fetch without touching components. Keys follow the `feature.screen.element` convention (femio-i18n-workflow); the brand wordmark "femio" stays Latin in every locale (product rule 6). AR/FR/ES scaffold strings are first-draft quality pending the portal's human-review workflow. Alternatives: stand up the DB-backed portal now (out of order, blocks scaffolding on P1.3/P1.19), or hardcode strings (violates i18n rule). Consequences: full locale routing + RTL working immediately; the DB migration is localized to one file. (→ apps/web/src/i18n/, ADR-007 §i18n)

## ADR-010 (2026-07-23): Anonymous mode via native Supabase anonymous auth, not device_key
Context: doc 14 §3.1/§4 sketched anonymous users keyed by a `device_key` claim, with RLS matching on that key. Supabase now offers **native anonymous sign-in**, which issues a real JWT with `role=authenticated` and a genuine `auth.uid()` (flagged `is_anonymous=true`). Decision: use **native anonymous auth**. Anonymous-mode users are `authenticated` and get full owner-only CRUD through the *same* `profile_id = auth.uid()` RLS as registered users; the Postgres `anon` role (no JWT) is limited to reading published content + UI strings. `handle_new_user()` provisions a `profiles` row for every new auth user, setting `account_type='anon'` when `is_anonymous`. Upgrading anon→registered keeps the same `auth.uid()`, so **no data migration** is needed (the merge problem in ADR-007's open list largely dissolves). `profiles.device_key` is retained (nullable, unused) for optionality. Alternatives: device_key claim (custom JWT plumbing, a second RLS path to audit, harder upgrade), local-only storage (no cross-device, weaker product). Consequences: one uniform RLS model; simpler, safer auth; requires enabling Anonymous sign-ins in the project (currently off — see runbook). (→ supabase/migrations/0002_rls_policies.sql, docs/runbooks/supabase_apply_migrations.md)

## ADR-012 (2026-07-23): Payload CMS as a separate app + content source of truth
Context: P1.6 needs a CMS for medical content (article/condition/FAQ/tip/glossary) in 4 locales with a draft→medical-review→publish workflow. doc 14 §11 left open "Payload vs Supabase as content source-of-truth," and Payload 3 can either co-locate inside the Next web app or run standalone. Decision: a **separate `apps/cms` Payload 3 app** (not co-located in `apps/web`), on the **shared Supabase Postgres** via the Postgres adapter. Rationale for separate: `apps/web` is already live with next-intl middleware + Serwist + its own plugin chain; bolting Payload's admin routes/plugins into it risks breaking a deployed app, and isolation matches doc 14's topology. **Payload owns authored content** and becomes the content source of truth — this supersedes the sketch `content`/`content_i18n` tables from migration 0001 (to be dropped in a later migration; `ui_strings` stays for the translation portal). Localization uses Payload's native locales (EN/AR/FR/ES, AR RTL). The **review gate is enforced at the data layer** (a `beforeChange` hook): only medical reviewers/admins can mark `approved`, and publish requires approval — so unreviewed content can't go live regardless of API. The web app will read published content via Payload's REST/GraphQL API (P1.8/P1.9). Alternatives: co-locate (better DX/Local API, but real risk to the live app + middleware/plugin conflicts); hand-rolled CMS on the existing tables (months of work); separate CMS database (loses one-DB simplicity, cross-DB joins). Consequences: two Vercel deploys + one shared DB; Payload needs the direct Postgres connection string (Khaled provides `DATABASE_URL` + `PAYLOAD_SECRET`); the 0001 content tables become dead and are queued for removal. (→ apps/cms/, docs/runbooks/cms_setup.md)

## ADR-013 (2026-07-24): Global crisis-safety routing — account-less, collect-nothing, WHO-adaptation-modeled
Context: Personas surface distress (self-harm ideation, abuse, grief, eating/body image). Femio needed one crisis-safety surface that is reachable everywhere, never gates help behind a questionnaire score or account, and stays out of medical-device scope. A country-by-country phone-number list was rejected as unmaintainable and error-prone (a wrong/stale number is a safety failure). Decision: a **global-only** interface — a persistent "Need help now?" launcher mounted in the locale layout (public + onboarding + calculators + signed-in) opening an accessible native `<dialog>`, plus a public account-less `/{locale}/help-now` page. The urgent route is always the reviewer-approved, verbatim wording from `docs/compliance/CRISIS_RESOURCES.md`: **contact local emergency services OR go to the nearest emergency department** (never a US/UK number as a global fallback). The approach is **modeled on WHO's global-to-local digital adaptation methodology (Digital Adaptation Kit pattern) — not a WHO endorsement of Femio's crisis content**; the doc cites WHO's suicide guidance as source, not sponsor. The interface **collects and transmits nothing**: `useCrisisHelp().open()` takes no reason/score/country/health-data payload, and there is **no analytics** anywhere on it (opening it could reveal mental-health intent). Copy is static/bundled so the dialog opens instantly and **offline**. Only English is human-approved; **ar/fr/es render the English fallback tagged `lang="en" dir="ltr"`** until a human linguistic reviewer signs off (status tracked in `crisis.json`; a CI guard, `scripts/crisis-compliance.mjs`, fails on expired copy [EN due 2027-07-23], approved-locale metadata gaps, or key-parity mismatches). The one outbound link (the maintained **Find A Helpline** directory) is **env-gated** (`NEXT_PUBLIC_CRISIS_DIRECTORY_URL`), hidden until set, locked by build-failing validation to the canonical `https://findahelpline.com` host with no query/fragment, opened with `referrerPolicy="no-referrer"` — pending confirmation of ThroughLine commercial/linking terms (CRISIS_RESOURCES § Directory policy); a missing link never blanks the crisis screen. Minors: account-less global availability is correct precisely because nothing is collected or reported. Alternatives: country phone packs (unmaintainable/unsafe — deferred to later verified market modules), gating help behind screener scores (unsafe), embedding/proxying the directory dataset (not licensed). Consequences: help is one tap away everywhere, in scope, privacy-preserving; **DPO + medical sign-off on the global-only posture is still required** (P0.12, DPIA §5) — this ADR + the DPIA line are the engineering record pending that. (→ apps/web/src/components/crisis/, apps/web/src/lib/crisis/, docs/compliance/CRISIS_RESOURCES.md)

## ADR-014 (2026-07-29): DB-overlay i18n loader — JSON base, approved-only overrides (P1.19)
Context: ADR-009 shipped UI strings as local JSON with the `request.ts` loader as the designated swap point for the DB-backed translation portal (`ui_strings`, applied in migrations 0001/0002). P1.19 needs the portal to actually serve strings without risking the live app or adding a per-request DB round-trip to every page. Decision: keep the **JSON catalogs as the base** and **overlay only `status = human_reviewed`** rows from `ui_strings` on top (deep-merged by dotted key). Consequences of the design: an unreviewed draft, an unseeded/empty table, or any DB error all leave the app on **pure JSON** — there is zero behaviour change until a string is deliberately approved in the portal, so the swap carries no regression risk (proven: the full 25/26 e2e suite passes with an empty table). The overlay read is wrapped in Next `unstable_cache` (one read per locale, `revalidate: 60`, tag `ui-strings`); the portals save action approves a string and calls `revalidateTag` so it goes live immediately. English stays the master (seeded `human_reviewed`, overlays identically to JSON); AR/FR/ES are seeded `machine` and only go live per-string as a human reviewer approves them (honours ADR-009s "AR/FR/ES are first-draft pending review"). The portal (`/[locale]/(app)/admin/translations`) is gated by `requireStaff(admin|translator)` (P1.18) with `ui_strings` staff-write RLS as the real boundary. Alternatives: hard cut JSON→DB (breaks the app if the table is empty/unavailable; no graceful degradation); serve all DB rows regardless of status (ships unreviewed machine drafts); no caching (a DB call per request/SSR). Deferred: DeepL machine-draft prefill (needs an API key) and richer in-context preview. Manual to activate: Khaled applies no new migration (table exists), grants a staff role to bootstrap review, and runs `scripts/i18n/seed-ui-strings.mjs` with a service key. (→ apps/web/src/lib/i18n/, apps/web/src/i18n/request.ts, scripts/i18n/seed-ui-strings.mjs)

## ADR-015 (2026-07-30): Publish Privacy + Terms as clearly-marked, noindex drafts (P1.9b.3)
Context: the content-first public site needs privacy and terms pages — they are the trust surface carrying Femio's headline differentiator (docs/13 §0), the onboarding consent flow will link them, and app stores / Search Console expect them. The *binding* text cannot exist yet: entity, DPO, EU representative, per-jurisdiction minor-consent ages, transfer mechanism, and liability/governing law all await counsel at the **P0.12 launch gate**, and Femio has no real users. Decision: publish both pages **now** as plain-language drafts that *say so on the page itself* — a warning banner ("Draft — not yet in force") naming exactly what is unsettled (company name, contacts, governing law, liability wording) — written from the docs/13 §3/§4 outlines, in all four locales, through the existing shared `TrustPage` component (extended with an optional notice + footnote). So a draft is never presented as Femio's policy of record, both pages are `robots: noindex, follow` **and excluded from the sitemap** — the inverse of every other public page, asserted by an e2e test. Flipping them to indexed + sitemapped is an explicit P0.12 deliverable (P0.12.4), not something to drift into. The copy states only what engineering can already evidence: EU hosting, explicit granular consent written before the first health row, owner-only RLS, in-app export/delete, no health data to ad or analytics SDKs, the 72-hour breach clock — so counsel edits wording, not facts. It passes the claims-language guard (no diagnose/treat/prevent/contracept), with the wellness boundary stated as "not a reliable way to avoid pregnancy", matching the reviewed calculator/tracker copy. Alternatives: ship nothing until counsel finishes (leaves the trust surface and the consent flow with nowhere to link, and hides a posture we are proud of); publish as if final (misrepresents an unsigned policy — the exact category failure Femio positions against); one combined legal page (worse readability, and stores/GSC expect separate documents). Consequences: honest, reviewable artifacts counsel can redline directly; the noindex + sitemap exclusion is deliberate and must be reverted with the finalized text; onboarding consent wording remains the acknowledged placeholder (P1.12.2). (→ apps/web/src/app/[locale]/(public)/{privacy,terms}/, docs/13_LEGAL_COMPLIANCE.md §3–§4, apps/web/e2e/legal.spec.ts)

## ADR-016 (2026-07-30): Author/reviewer bios as a standalone `people` CMS collection (P1.9b.3b)
Context: doc 15 §7/§8 requires every published health page to name its **author** and its **medical reviewer with credentials**, each linked to a **bio page carrying `Person` schema with `sameAs` professional profiles** — the E-E-A-T backbone for a YMYL category. The CMS already has a `users` collection (CMS logins with roles) and `editorialFields.medicalReviewer` points at it, but a login is not a public identity: not every reviewer needs CMS access, a byline needs localized name/credentials/biography and public profile links, and publishing account records would leak staff account data. Decision: a **standalone `people` collection** — name (localized, because names transliterate per script), shared slug, roles (author / medical reviewer), credentials, job title, affiliation, rich-text bio, optional portrait, and a `sameAs` array of professional-profile links. It deliberately does **not** use `contentCollection`: a bio is not medical content, so it carries no sources/disclaimer/review-status fields and no medical-review publish gate — but drafts stay on, so a bio is public only once published, and the same `readPublishedOrStaff` access rule applies. The web app reads it through the existing graceful CMS client (`listPeople`/`getPersonBySlug`) and renders `/{locale}/authors` (index, honest empty state) + `/{locale}/authors/[slug]` (Person + BreadcrumbList JSON-LD, ISR, sitemapped). Alternatives: publish bios from `users` (couples public identity to CMS logins, leaks account records, no localized byline fields); hardcode bios in the repo (editors can't maintain them, defeats the CMS); defer entirely until P1.9 (leaves articles unable to link a byline the moment the first one publishes). Consequences: **no columns were added to existing collections**, so the live CMS keeps working, but Payload's interactive push means the `people` tables need one local `pnpm --filter cms dev` before that screen opens (runbook C3.6 / cms_setup Step 6) — until then the website's `/authors` simply shows its empty state. Wiring bylines *onto* articles (article → author/reviewer relationships + the byline block on the article page) lands with the first P1.9 content, as does portrait rendering (needs `images.remotePatterns` for the CMS host). (→ apps/cms/src/collections/People.ts, apps/web/src/app/[locale]/(public)/authors/, apps/web/src/lib/seo/jsonld.ts)

## ADR-017 (2026-07-30): Analytics as a closed enum catalog, not a convention (P1.20)
Context: P1.20 asked for an "anonymized analytics dashboard (PostHog embed: age bands, mode, condition tags, retention, funnels)". Two problems surfaced on starting it. First, those named dimensions are the violation: docs/13 §5 forbids sending health data to a third-party analytics SDK "ever", and a condition tag, life-stage mode, or age band attached to a pseudonymous `distinct_id` is special-category data under GDPR Article 9 — this is what the FTC pursued Flo (2021) and Premom (2023) for, ordinary product analytics carrying reproductive data while the policy said otherwise. Second, the existing consent purposes are `core/insights/research`; there is **no** analytics purpose, and `insights` ("use my entries to show me patterns") is first-party processing of her own data, so reusing it as permission to send events to a vendor would be precisely that purpose creep. Decision: build the event layer so the unsafe payload is *unrepresentable* rather than merely discouraged. The catalog (`lib/analytics/events.ts`) is closed — a fixed event list, fixed property keys per event, and every value drawn from an enumerated literal, with **no free-form string, number or date anywhere in the schema**, so an article slug, symptom label, cycle date or lab value has no channel to travel down. A runtime guard re-validates every payload because types are erased at runtime, with a health-term denylist as a second belt. `pnpm analytics-lint` (new CI step) is the ratchet against future drift: health-shaped property names, free-form `string`/`number` properties, autocapture or session recording, or any attempt to track the crisis surface all fail the build. Both the guard and the lint **tokenize** identifiers (split separators + camelCase, prefix-match tokens) rather than using `\b`, because an underscore is a word character so `/\bcondition\b/` misses `condition_tag` — the first lint draft used `\b` and silently passed an injected `condition_tag`; short ambiguous stems (`lab`, `age`) are matched as whole tokens so they don't fire on `label`/`page`/`language`. Analytics gets its own opt-in `analytics` consent purpose (migration 0005) and fails closed. Residency is enforced, not documented: PostHog's SDK defaults to its **US** host, so a non-EU host or a key without a host **fails the build** (verified: US host → exit 1, key alone → exit 1, `eu.i.posthog.com` → exit 0). The dimensions PostHog must never hold move to a first-party dashboard over our own RLS-protected Postgres with k-anonymity thresholds (P1.20.3) — that is the real "anonymized analytics dashboard" the original line wanted. Alternatives: free-form events with a code-review convention (one careless `page: pathname` leaks every article slug — the actual Flo failure mode); autocapture for speed (scrapes DOM text, defeating any catalog); gate on `insights` (purpose creep); wire PostHog now and filter later (loading a vendor SDK before a signed DPA and a consent toggle is itself the violation). Consequences: no vendor script loads today and `track()` is a verified no-op, which is correct rather than provisional; the useful product questions (per-calculator demand, retention by life-stage) are deliberately *not* answerable from PostHog and wait on P1.20.3; adding an event is a compliance change requiring doc 19 + data-map updates in the same PR. (→ apps/web/src/lib/analytics/, scripts/analytics-lint.mjs, supabase/migrations/0005_analytics_consent_purpose.sql, docs/19_ANALYTICS_EVENT_SCHEMA.md)

## ADR-018 (2026-07-30): CMS staff roles are bootstrapped out-of-band; production schema push is a temporary convenience
Context: verifying the P1.9b.3b `people` tables against the live database surfaced two things about the deployed CMS. (a) **Role deadlock:** `payload.users` holds exactly one account, roles `{editor}`. Payload's "create first user" screen bypasses `create: isAdmin` but still applies the field default `["editor"]`, and `roles` carries `access: { update: isAdminField }` — so with no admin anywhere, nothing inside the admin panel can promote anyone, and an editor can neither approve nor publish (the review gate requires `admin|medical_reviewer`) nor manage users. The CMS was effectively draft-only. (b) **Schema push in production:** the `people` tables appeared without the local push the runbook asked for, because `PAYLOAD_DB_PUSH=true` is still set on the `femio-cms` Vercel project — additive changes skip Payload's interactive prompt, so the deploy created them (verified: column shapes match the collection; `GET /api/people` → 200). Decisions: (a) staff roles are repaired **out-of-band by a committed script**, `apps/cms/scripts/set-user-roles.mjs` (`pnpm --filter cms set-roles`), which goes through Payload's **Local API with `overrideAccess`** so hooks, validation and password hashing behave exactly as in the panel — no hand-written SQL against Payload's tables, and reviewable in git rather than an invisible database edit. It also accepts `NEW_PASSWORD` because the CMS has no email transport, which makes Payload's forgot-password flow undeliverable. This is deliberately the CMS twin of the `staff_roles` SQL bootstrap (runbook B2): first-privilege grants live outside the app that they gate. Claude authored it but the permission layer blocks it from running privilege changes against the production database, so the single command stays Khaled's (runbook C3.7) — the right split anyway. (b) `PAYLOAD_DB_PUSH` **stays on for now** (the content model is still moving; P1.9 will add fields, and additive auto-creation is what just saved a manual step) and is removed as part of a switch to `payload migrate:create`/`migrate` **before real content exists** (P1.6.5) — because the failure mode is asymmetric: additive changes are safe, while a removed or renamed field is exactly the case a non-interactive deploy cannot confirm, and could drop a column of published content. Alternatives considered: promote the user with direct SQL against `payload.users_roles` (bypasses hooks, silently drifts from Payload's expectations, unreviewable); add a seeding hook that force-grants admin on boot (a permanent privilege-escalation path in production code); relax the `roles` field access so editors can self-promote (defeats RBAC). Consequences: publishing is unblocked by one documented command; the review gate still needs a **separate `medical_reviewer` account** so content isn't self-approved (P1.9.0, doc 15 intent); and prod schema management has an explicit expiry date rather than an accident nobody noticed. (→ apps/cms/scripts/set-user-roles.mjs, docs/runbooks/OWNER_MANUAL_TASKS.md C3.6–C3.7, docs/runbooks/cms_setup.md Steps 6–7)

## ADR-019 (2026-07-30): Consent is a reduction over an append/revoke-only ledger, and withdrawal lives in Settings (P1.20.2)
Context: P1.20 shipped an `analytics` consent purpose that fails closed, but nothing ever asked for it — onboarding offered core/insights/research only, so `track()` was off for everyone and would have stayed off. Building just an analytics checkbox would have exposed a worse gap: **no optional consent could be withdrawn anywhere in the product**. `insights` and `research` were granted once during onboarding and then frozen, which fails GDPR Art. 7(3) ("as easy to withdraw as to give") on a special-category dataset. Decisions: (a) consent state is computed as a **reduction over the `consent_records` ledger** — newest row per purpose wins, and a row counts only if `granted = true` **and** `revoked_at is null` — expressed once as pure functions in `lib/consent/purposes.ts` and reused by the analytics gate, so the UI and the gate cannot drift; absence of a row is a **no**, which is the normal state for every user who predates a purpose. (b) Withdrawal **stamps `revoked_at` on the live grant and appends an explicit `granted = false` row**: the timestamp is what an audit or DSAR asks for ("when did permission end"), while the appended row means the current answer is readable without interpreting history. The ledger is never rewritten or deleted — 0002 grants select/insert/update and deliberately no delete. (c) The Settings surface covers **every optional purpose**, not just analytics, in the same words onboarding used; **core is displayed but not switchable**, because it gates every health write in RLS, so the honest way to withdraw it is account deletion (linked directly below it) rather than a switch that would either lie or silently brick the app — a dark pattern in the other direction. (d) `CONSENT_VERSION` moves to `lib/consent` and is bumped to the date purposes changed, so onboarding and Settings can never record different versions of the same wording. Alternatives: a boolean column per purpose on `profiles` (loses when and what version was agreed — the ledger *is* the evidence); an analytics-only toggle (leaves insights/research unrevokable); treating `insights` as covering analytics (the exact purpose creep the FTC pursued Flo for — a unit test now pins that one purpose never implies another). Consequences: analytics consent can be granted and withdrawn, and both survive a reload (proven by a live e2e against the real ledger); the wording is a faithful placeholder pending counsel (P1.12.2); `track()` still needs a configured EU key on top of consent, so nothing is sent today. (→ apps/web/src/lib/consent/, apps/web/src/components/account/consent-settings.tsx, apps/web/e2e/consent.spec.ts)

## ADR-020 (2026-07-30): The product dashboard is first-party, aggregate-only SQL with secondary suppression (P1.20.3)
Context: ADR-017 established that the dimensions the original P1.20 line asked for — life-stage mode, condition/persona tag, age bands, cohort retention — can never come from PostHog, because attached to a pseudonymous id they are special-category health inferences that docs/13 §5 forbids sending to a third-party SDK. So the real "anonymized analytics dashboard" has to be built over Femio's own Postgres. That runs into the deliberate obstacle that staff **cannot read those rows**: RLS is owner-only, and nobody at Femio should be able to page through a woman's symptom log. Decision: three `security definer` functions in migration **0006** that read the rows and return **only `(label, count)`** — no id, date, symptom, slug or note has a return path — each performing its own `is_staff(auth.uid(), array['admin'])` check *inside* the security-definer boundary (the caller is not trusted to do it), with execute revoked from `anon`. The web page reads nothing else: `lib/insights/queries.ts` calls only these RPCs, so the dashboard cannot show what SQL did not aggregate. Anonymity is enforced at two levels for one reason — the first is not enough. **Primary suppression** hides any group below k (10). **Secondary suppression** exists because hiding a cell does not hide its value when the rest of a table can be subtracted from a published total: the first validation run showed exactly this — 56 accounts with "anonymous = 55" visible makes "registered = 1" arithmetic. So breakdowns now absorb the smallest *visible* group into the `withheld` bucket, repeatedly, until that bucket itself clears k and merges ≥2 groups, and complementary overview metrics (registered/anonymous, which sum to the total) are suppressed together. A dimension that cannot be made anonymous returns nothing at all, and the UI says "not enough people yet" rather than rendering a suppressed cell as zero — "no data" and "too few people" are different claims. The k rule is re-applied in TypeScript (`lib/insights/k-anon.ts`, 9 tests) for the same reason `analytics/guard.ts` re-validates typed events: a privacy guarantee should not rest on one layer staying correct. Verification approach worth keeping: the migration was executed against the **live schema inside a transaction that was rolled back**, which caught a `sum()`-returns-`numeric` type mismatch and the differencing leak that code review had missed — authoring SQL by hand and shipping it unrun is how a migration reaches the owner broken. The RLS audit gained three checks that a non-staff caller is refused, labelled `[SKIPPED]` when 0006 isn't applied so an unapplied migration can never read as a green access-control check. Alternatives: PostHog with these dimensions attached (forbidden, and the reason this exists); a service-role key in the app to bypass RLS wholesale (a master key in a request path, to avoid writing three functions); materialized views (a second copy of health-derived data to secure and refresh); no suppression, "staff can be trusted" (the point of k-anonymity is that a staff account is one compromise away from being someone else's). Consequences: staff answer product questions without any per-person access; the numbers stay in the EU database and are never sent to a vendor; on today's small user base most cells are correctly withheld, which is the guard working, not a bug; Khaled applies 0006 (runbook A3). (→ supabase/migrations/0006_insights_aggregates.sql, apps/web/src/lib/insights/, apps/web/src/app/[locale]/(app)/admin/insights/)

## ADR-021 (2026-07-31): Dependency ratchet, security headers, and rendering content detail routes dynamically (P1.23)
Context: P1.23's open items included dependency scanning, a CSP/headers review, and MFA. Starting the first two surfaced a third, worse problem. **Dependencies:** `pnpm audit` reported 15 advisories including a critical (vitest) and five highs. Decision: fix what can be fixed — vitest 2→4, sharp 0.33→0.35, Next 15.1→15.5 — and pin the rest through `overrides` in **`pnpm-workspace.yaml`** (pnpm 11 reads settings there, not from `package.json`, which is why the first attempt silently did nothing), each override annotated with the advisory it answers. That took 15 → 3. What remains is declared, not hidden: `auditConfig.ignoreGhsas` carries the one accepted residual (brace-expansion@1 under ESLint/Serwist tooling, expanding globs we author ourselves, no 1.x patch published) with a reason and a review date, and CI runs `pnpm audit --audit-level high`, so a *new* advisory fails the build while a known one can only stay green by being written into a diff. Dependabot is deliberately narrow — grouped weekly PRs, majors excluded (a framework major is a verified migration, not an automated PR) — because update fatigue is how security PRs start getting rubber-stamped. Vitest 4 needed `oxc: { jsx: … }` in its config: Vite 8 transforms with oxc, and Next's `jsx: "preserve"` tsconfig otherwise breaks any test importing a `.tsx` module. **Headers:** a full set in `next.config.mjs` — CSP, HSTS (no `preload`: irreversible on a domain that isn't final), `frame-ancestors 'none'` (clickjacking a health app is a real risk), `Referrer-Policy: strict-origin-when-cross-origin` (a Femio URL like `/learn/endometriosis-symptoms` is itself a health inference), Permissions-Policy, and `poweredByHeader: false`. `connect-src` is built from the same env the app reads, so the allow-list cannot drift from the services in use — that directive is what actually enforces "no health data reaches a third party" at the browser level. `script-src` keeps `'unsafe-inline'`: the strict alternative is a per-request nonce, which forces dynamic rendering site-wide and would cost the static generation this SEO-first site depends on; `'unsafe-eval'` is granted to the dev server only, asserted in both directions by e2e. **The bug this uncovered:** running the e2e suite in CI mode (`next start`) rather than dev exposed that **every unknown slug under `/learn`, `/conditions` and `/authors` returned 500, not 404** — live for weeks. Cause: `notFound()` thrown from a statically-rendered route makes next-intl resolve the locale from `headers()` during the not-found pass, a dynamic API that is illegal there (`DYNAMIC_SERVER_USAGE`). Decision: render those three detail routes per-request (`force-dynamic`) and add the localized `[locale]/not-found.tsx` that P1.2.2 had deferred. The cost is HTML assembly per request — the CMS fetch keeps its own 5-minute cache — and the alternative was 500s on every stale or mistyped content URL, which is worse for users and for crawlers. Alternatives rejected: pre-generating all slugs with `dynamicParams: false` (new articles would need a deploy, defeating the CMS); leaving it (a 500 on any renamed article). Consequences: a real class of production failure is now covered by tests that run in the same mode CI does; three routes trade static delivery for correctness until next-intl v4 (P1.23.2) lets ISR and `notFound()` coexist; the pattern to keep is that **dev-mode e2e is not evidence about production** — the suite must be run with `CI=1` before pushing. (→ pnpm-workspace.yaml, .github/dependabot.yml, apps/web/next.config.mjs, apps/web/src/app/[locale]/not-found.tsx, apps/web/e2e/{security-headers,not-found}.spec.ts)

## ADR-022 (2026-07-31): next-intl v3 → v4, and the ISR/`notFound()` workaround stays (P1.23.2)
Context: two moderate advisories sat on next-intl v3 — an **open redirect** (GHSA-8f24-v5vv-gm5j) and prototype pollution via precompiled catalogs (GHSA-4c35-wcg5-mm9h). The open redirect is the one that matters: it is user-facing, and a phishing hop through a health domain costs exactly the trust Femio is built on. Both are fixed only in v4.9+. ADR-021 additionally *expected* v4 to let `notFound()` work under static rendering, which would let the three CMS detail routes drop `force-dynamic`. Decision: upgrade to **next-intl 4.13**. The migration needed **no application changes** — the codebase had already adopted the v4-shaped APIs (`defineRouting`, `createNavigation`, awaited `requestLocale`, an explicit `locale` returned from `getRequestConfig`), which is the payoff for having followed the deprecation warnings at the time. Two things did change: the layout now lets `NextIntlClientProvider` **inherit messages from the request config** (v4 behaviour) instead of passing them explicitly, and v4 pulls `@swc/core` + `@parcel/watcher`, whose postinstall scripts are recorded as **deliberately not built** in `pnpm-workspace.yaml` — both ship prebuilt platform binaries, so compiling from source buys nothing and a skipped postinstall is one less piece of arbitrary code at install time. The audit is now at **zero advisories**, down from 15 at the start of P1.23. **The expectation about ISR was wrong, and testing it is the point:** with v4 installed, reverting one route to `revalidate = 300` still produced `DYNAMIC_SERVER_USAGE` → 500 on an unknown slug, while the `force-dynamic` route returned 404. So the workaround stays, and that result is now written next to the workaround in each of the three files, so the next person doesn't retry it on a hunch. Restoring static rendering there needs a different fix — most likely a root `app/layout.tsx` + locale-less `app/not-found.tsx` so the not-found pass never needs a request locale — tracked as P1.23.2b, not urgent: per-request rendering costs HTML assembly, and the CMS fetch keeps its own five-minute cache. Consequences: the last known dependency advisories are cleared; the i18n surface is on a supported major; the 404 behaviour verified in ADR-021 is unchanged (55/55 DB-free + 9/9 live e2e in production mode). (→ apps/web/package.json, apps/web/src/app/[locale]/layout.tsx, pnpm-workspace.yaml)

## ADR-023 (2026-07-31): Two-step sign-in — enforced for staff, offered to everyone (P1.23.3)
Context: SECURITY_REVIEW A07 has carried "MFA for staff/admin accounts" since the security pass began. A back-office session can read the translation portal and the aggregate insights, and an **admin can grant roles** — so a stolen staff password is, today, enough to escalate. Supabase provides TOTP factors and models the result as assurance levels, where `next` is what the account is capable of and `current` is what this session has actually done. Decision: **enrolment is offered to every signed-in account** (a woman's health record is worth a second factor whoever owns it, and the UI is identical), while **enforcement applies to staff routes only** — `requireStaff` now resolves the MFA status after the role check and redirects anything short of `aal2`. The policy lives in a pure function (`staffMfaRedirect`, 11 unit tests) rather than inside the guard, so it can be read and tested as a rule: a verified session passes; an enrolled-but-not-stepped-up session goes to `/{locale}/mfa` carrying its destination; an **un-enrolled** staff member goes to **Settings**, not to a dead end. That last branch is what makes hard enforcement safe: Settings is not staff-gated, so there is no state in which the only admin cannot reach the form that fixes their own lockout — the usual argument against enforcing MFA on a single-admin system doesn't apply. Details that matter: the step-up destination is **locale-less** (`/admin/insights`), because the challenge navigates with the i18n router which adds the prefix — passing a prefixed path would produce `/en/en/...`; the `next` parameter is filtered by the same same-origin guard used on the auth callback, since an unvalidated post-login redirect is an open redirect; abandoned enrolments leave `unverified` factors behind, which are cleared before a retry so a half-finished scan can't block a second attempt; and only `verified` factors count as enrolled, or an abandoned enrolment would demand a step-up the account cannot satisfy. The QR is an inline SVG data URI, already permitted by the CSP's `img-src data:` (ADR-021). Alternatives: enforce MFA for all users (hostile to an anonymous-first product whose core promise is tracking without an account); leave it advisory (the review item asks for a control, and a warning is not one); WebAuthn/passkeys (better UX and phishing-resistant, but a bigger surface and Supabase's TOTP path is the one available now — worth revisiting). Consequences: **Khaled must enrol before `/admin/*` opens again** — flagged in the runbook rather than left to be discovered; the same enrolment card protects consumer accounts that want it; recovery codes are not implemented, so a lost authenticator needs an admin-side factor reset (tracked P1.23.3b). (→ apps/web/src/lib/auth/mfa.ts, require-staff.ts, components/account/mfa-settings.tsx, components/auth/mfa-challenge.tsx, app/[locale]/(app)/mfa/)

## ADR-024 (2026-08-01): MFA recovery lives outside the app; the global error boundary carries bundled copy (P1.23.3b, P1.2.4)
Context: two loose ends from the security pass, both about what happens when the normal path fails. **(a) Lost authenticator.** ADR-023 made a second factor mandatory for staff routes, and Supabase offers no self-service factor reset — so a staff member whose phone dies is locked out of the back office, and "ask the other admin" is not a plan while there is exactly one admin. Decision: `scripts/auth/reset-mfa.mjs`, a service-key script that lists a user's factors and deletes them, with `DRY_RUN=1` to look before acting. This is the same shape as the `staff_roles` SQL bootstrap and the CMS role script for the same reason: **first-privilege recovery has to live outside the thing it recovers**, or it is not recovery. It removes factors only — password, roles and data are untouched — and the account is expected to re-enrol immediately, which the script's own output says. The admin API surface (`auth.admin.mfa.listFactors` / `deleteFactor`, and the `data.factors` response shape) was verified against the installed client rather than assumed, because a recovery tool that reports "no factors" when it means "I called the wrong method" is worse than no tool. **(b) Global error boundary.** `global-error` replaces the *root layout* when a render fails above every other boundary, so nothing from that layout exists at that moment: no `NextIntlClientProvider`, no theme, no guaranteed stylesheet. Decision: **bundled copy in four locales and inline styles**, locale read from the URL path — the same reasoning as the crisis dialog (ADR-013): a surface that only appears when things are broken must not depend on the machinery that broke. Verified by deliberately throwing from a temporary route and loading it in a real browser: 500 status, correct copy, and **RTL in Arabic**, with a working retry. Worth stating plainly: Next serves a minimal `__next_error__` shell server-side and mounts this boundary on the client, so the branded copy appears after hydration and a visitor with JavaScript disabled sees a bare 500 — framework behaviour, not something this component can change. The probe route was deleted; an automated e2e would require shipping a permanent fault-injection route, which is not worth a public surface that exists only to break. Consequences: enforcing MFA no longer creates a one-way door; the last framework-default screen a user could hit is now branded and translated. (→ scripts/auth/reset-mfa.mjs, apps/web/src/app/global-error.tsx)
## ADR-025 (2026-08-03): The PostHog transport — lazy-loaded after consent, with the vendor's own properties filtered (P1.20.1)
Context: the event layer (ADR-017) was built with a deliberate seam and no vendor behind it. With an EU key configured, that seam had to be filled — and filling it is where the actual privacy risk lives, because the guarantees so far only covered **what Femio attaches to an event**. Decision, two parts. **(a) The SDK is imported dynamically inside `capture`,** which runs only after `track()`'s consent gate has passed. This is what makes docs/13 §6 ("no non-essential SDK fires before consent") literally true rather than approximately: for a visitor who never opts in, `posthog-js` is not idle — it is **never fetched and never executed**. Initialising at module scope would have looked identical in review and quietly broken the promise, so the lint now fails a static import. **(b) `sanitize_properties` filters the vendor's automatic properties.** This is the part that matters most and the part a closed event catalog does *not* cover: `posthog-js` appends `$current_url`, `$pathname`, `$referrer` and UTM values to every capture by default, and on Femio a URL **is** health data — `/en/learn/endometriosis-symptoms` attached to a persistent `distinct_id` is a health inference about a person, precisely the pattern the FTC pursued Flo and Premom over. The filter is **deny-by-default** (an allow-list of our own declared keys plus a short list of pseudonymous vendor identifiers) rather than a blocklist, so a property added by a future SDK release cannot ride along; the forbidden names are additionally listed by hand so the *reason* survives in the source, and each is asserted in a test. Everything else is subtraction: autocapture off (would scrape symptom labels and article titles from the DOM), session recording off (would record health fields on screen), `capture_pageview` off (that *is* the URL — we send a coarse `area` from the catalog instead), `persistence: localStorage` (no analytics cookies at all, so there is nothing to disclose in a banner), `advanced_disable_decide` (skips a round trip for feature flags we don't use). The lint ratchet gained three rules — pageview capture, a missing sanitizer, and a non-dynamic import — and **each was verified to fail when deliberately broken**, because a guard that cannot fail is decoration (the same lesson as the claims-lint false pass). Alternatives: a reverse proxy through our own domain (defeats the CSP allow-list as a control and makes the data flow less legible, not more); sending pageviews and stripping the path server-side in PostHog (trusts the vendor's pipeline with data that should never have left the browser); no analytics at all (defensible, but the product questions are real — they are simply answered first-party where they involve health, per ADR-020). Consequences: with the key set, allow-listed events from consenting users now actually reach PostHog EU; nothing changes for anyone else; and the remaining gate before this is switched on for real users is the **signed DPA** (docs/13 §5, processor register). (→ apps/web/src/lib/analytics/{transport,sanitize}.ts, scripts/analytics-lint.mjs)

## ADR-026 (2026-08-03): Sentry ships scrubbed — route patterns, no bodies, no user, EU-only (P1.4.2)
Context: P1.4.2 has wanted error monitoring since CI was set up, and the hydration crash that took down every signed-in page is exactly the class of bug it catches. The obstacle was never the install: **Sentry's defaults are wrong for this product.** Out of the box it collects the failing URL, request bodies, cookies and navigation breadcrumbs — and on Femio each of those is a health disclosure. `/en/learn/endometriosis-symptoms` says what she was reading; the body of a failed POST *is* the symptom, date or note she just entered; breadcrumbs replay the same URL trail in sequence. Sentry is a processor under docs/13 §5, and health data does not reach processors. Decision: wire it, but cut the payload down to **which route broke and what the error was**. The load-bearing idea is that URLs are **normalised to route patterns rather than dropped** — `/en/learn/endometriosis-symptoms` becomes `/[locale]/learn/[slug]`, which keeps the entire debugging value (you know precisely which page failed) while destroying the inference (you cannot tell which article, or even which language she reads in). Dropping URLs outright would have made reports much harder to act on and pushed someone to re-add them later; this way the safe form is also the useful one. Around that: `beforeSend` deletes request bodies, cookies, query strings and `extra` (free-form by definition, therefore unauditable), keeps only `user-agent`/`content-type` headers, and removes `user` entirely — Sentry does not need to know *who* hit a bug to help us fix it, and a user id joined to a route is the start of a profile. Tracing is off (spans carry URLs and we are not diagnosing latency yet) and session replay is off (it would record the tracker screen outright). Residency follows the same posture as PostHog and the crisis link: a DSN that is not an **EU ingest** host **fails the build** — Sentry's US cluster is the default a copied DSN lands on, and nothing in a running app would look wrong. Verified by supplying a US DSN: exit code 1 with the reason printed. The CSP `connect-src` gains the ingest origin **derived from the DSN**, so the policy cannot drift from the project in use, and an unparseable DSN widens nothing. Alternatives: the Sentry wizard's default config (would have shipped PII and replay); server-side scrubbing via Sentry's data-scrubbing rules (trusts the vendor's pipeline with data that should never have left the browser — and the DPIA claim is that it doesn't leave); no error monitoring (leaves us finding production faults from user reports, which is how the 500-instead-of-404 survived for weeks). Consequences: 18 unit tests pin the scrubber, including that a symptom body and an article slug cannot survive it; source-map upload is deliberately **not** configured (it needs an auth token and `@sentry/cli`'s postinstall, so stack traces stay minified for now — P1.4.3b); and the DSN must be set in Vercel for any of this to activate. (→ apps/web/src/lib/observability/{scrub,dsn}.ts, instrumentation.ts, instrumentation-client.ts, next.config.mjs)

## ADR-027 (2026-08-03): Event call sites declare an area; there is no code path from a URL to an event (P1.20.4)
Context: the analytics pipe was complete — catalog, runtime guard, consent gate, PostHog transport — and reported nothing, because nothing in the app called `track()`. Wiring the call sites is where a well-designed schema usually leaks anyway, since the obvious implementation is a route-aware hook: read `usePathname()`, send the page. That is precisely how `/learn/endometriosis-symptoms` ends up attached to a pseudonymous id. Decision: **the page declares its area as a literal**, and no analytics code ever reads a path. `<PageView area="library" />` is typed to the catalog's seven values, so the compiler rejects anything else, and there is no function anywhere that converts a URL into an event — the leak is not merely discouraged, it is absent. Mounted in **shared components rather than on 25 pages** (`TrustPage`, `ContentHub`, `ContentArticle`, `CalculatorLayout`, the `(app)` layout), which keeps a new page correctly instrumented by default and means the mapping can't drift page by page. Because layouts persist across navigation within a segment, an "area view" fires on *entering* an area rather than per page — which is the honest granularity: per-page counting would require per-slug identity, which is the thing we refuse to send. Funnel events follow the same subtraction. `signup_completed` carries `auth_method` and `outcome` but **not `mode`** — life stage is health data (it is answered first-party, ADR-020). `signin_completed` carries method and outcome, never the email or user id. Google sign-in fires only on *failure*, because success navigates the browser away to Google and the return trip already registers as an `app` area view — double-counting would be a measurement bug, not a privacy one, but it is worth stating why the branch is asymmetric. `calculator_used` fires **once per visit** via a `useRef` latch, since every calculator recomputes on each keystroke and an un-latched event would turn a usage count into a typing-speed measurement; it deliberately omits *which* calculator, because "used the due-date calculator" implies pregnancy and "fertile window" implies trying to conceive. The crisis surface has **zero** call sites, enforced by the existing lint rule (ADR-013). Alternatives: a route-aware `usePathname` hook with a slug denylist (one forgotten route away from a leak, and the denylist grows with the site); server-side page tracking (moves the same URL problem to a place with even less scrutiny); tracking nothing until launch (the pipe would then be first exercised under real traffic, which is the worst time to discover a mistake). Consequences: analytics now reports for consenting users, and the PostHog key becomes verifiable from outside because a client module finally imports `track`; 18 call sites total; anything new inherits the area from its layout. (→ apps/web/src/components/analytics/page-view.tsx, lib/analytics/use-calculator-used.ts)

## ADR-028 (2026-08-03): Femio is a health product, not a medical one — reduce the framing, keep the boundary (owner direction)
Context: Khaled's direction — "I do not need to be a medical website with its restrictions, but a health one; limit the use of medical and medicine wordings and highlight the disclaimer." An audit found 28 user-facing strings using *medical/medicine/clinical*, and they turned out to be two entirely different things wearing the same word. Decision: **separate the framing from the boundary, and move them in opposite directions.** (a) **Decorative framing** — "Medically-reviewed guides", the "Medically reviewed" badge, the "Medical review" nav label, "Medical reviewer" as a role — makes Femio sound like a clinic, which is both off-brand and, given that we are deliberately outside medical-device scope, slightly dishonest. These become **clinician**-framed: "Clinician reviewed", "How we review", "Clinician reviewer". This is not a weakening — naming the *person* who checked the page is more specific and more verifiable than the adjective "medical", and it is exactly what doc 15 §7/§8 asks for (a named clinician with credentials and a bio link, now shipped in P1.6.6). (b) **Boundary statements keep the word `medical`, verbatim** — "not medical advice", "not a substitute for your clinician", "not a medical device", "seek urgent medical care". Those sentences are the regulatory protection, not decoration; softening them to sound friendlier would trade away the exact thing the positioning depends on. The rule that resolves any future case: *medical framing is decoration and can go; the medical boundary is protection and stays.* (c) **The boundary moves earlier.** Article pages previously showed the disclaimer only after the body; a short boundary line now sits directly under the byline, so a reader knows what she is reading before she acts on it rather than after. The full disclaimer box remains at the end. Deliberately unchanged: `MedicalWebPage` structured data and the `/medical-review` URL. Schema is a machine-readable *classification* of the page's subject, not a claim made to a reader, and it is what makes health content legible to search engines under YMYL rules; changing the URL would cost redirects for no reader benefit while its visible label already reads "How we review". Consequences: the content brief gained a positioning section (the assistant is drafting against it now), so the 60 articles are written in health voice from the first batch rather than being edited into it later; four locales updated; a bug was found and fixed on the way (see below). (→ apps/web/messages/*.json, components/cms/content-article.tsx, docs/content/CODEX_AUTHORING_BRIEF.md §1)

## ADR-029 (2026-08-03): Deploy-time schema push is not a deployment strategy — incident and correction (P1.6.5, P1.6.6b)
Context: adding public authorship + SEO fields to Articles and Conditions (P1.6.6) took **production down**: both collections returned 500, the one published article went offline, and only the collections I had changed were affected — `people`, `faqs` and `glossary` stayed healthy, which isolated the cause immediately. The deployed CMS expected columns the database did not have. What made the mistake easy: `PAYLOAD_DB_PUSH=true` had silently created the entire `people` table set on deploy a few days earlier (ADR-018 recorded that as a convenience and flagged the risk), so "additive changes apply themselves" had become an assumption backed by exactly one observation. A `hasMany` relationship needs more than columns — it needs a new `articles_rels` table — and that did not apply in a non-interactive deploy. Decision, in order: **(a) restore first.** Reverting the two `publishing: true` lines brought the API back; the field definitions and the web-side rendering stayed in place, because they read the fields as optional and render nothing when absent, so re-landing costs one line per collection once the schema is real. Rolling *forward* by hand-writing the missing DDL was rejected — reproducing Payload's expected relationship tables and enums by hand is the error-prone path this project has avoided twice already. **(b) The generalisable lesson:** deploy-time schema push is not a deployment strategy, it is a development convenience that happens to work until it doesn't, and it fails *at the moment of deployment* with no rollback of its own. P1.6.5 (switch to `payload migrate:create` + `migrate`, drop `PAYLOAD_DB_PUSH`) moves from "before real content" to **urgent**, and P1.6.6b re-lands the fields through a migration. **(c) A verification gap of mine:** I verified the *code* thoroughly — build, typecheck, 154 unit tests, 57 e2e — and none of it could see the database, because the CMS build deliberately doesn't connect. The check I skipped was the cheap one: hit the deployed API after the deploy. Every previous CMS change in this project was verified that way; this one wasn't, and the regression lived for roughly an hour. ## ADR-030 (2026-08-04): The 45-minute CMS build "hang" was an interactive prompt — diagnosis and correction (P1.6.5b)
Context: every `femio-cms` deploy from 33ec508 onward ran until Vercel's 45-minute build timeout and failed, and `pnpm --filter cms migrate` appeared to hang locally too. 685d25f concluded that "payload migrate does not complete in this setup", removed the migrate step from the build, and made migrations a deliberate manual act. ## ADR-033 (2026-08-04): A concurrent session silently reverted MASTER_TODO — caught, restored, and worth a habit
Context: `docs/07_MASTER_TODO.md` went from 202 lines to 178 in commit `bb0f0a5`, reverting to a state predating 2026-07-31 and erasing the completion records for roughly two sessions of work — P1.2.2, P1.2.4, P1.4.3, P1.6.5, P1.6.6, P1.6.6b, P1.6.7–P1.6.13, P1.9c, P1.20.1, P1.20.4, P1.23.1–P1.23.4 and P1.26.1a among them — along with the edits that commit was supposed to be adding. ## ADR-034 (2026-08-04): Clearing the dependency ratchet — and why an override target must be bounded (P1.23.1)
Context: CI had been failing on every commit at the `pnpm audit --audit-level high` step — **10 advisories, 5 high** — nothing to do with the changes being pushed. This is the P1.23.1 ratchet behaving exactly as designed: the tree was at 0 advisories on 2026-07-31, and four new highs were published against transitive dependencies since. Decision: fix all four with pinned overrides in the established pattern — `undici` >=7.29.0 (GHSA-4cwx-7wf7-3272, via `payload`), `fast-uri` >=3.1.5 (GHSA-7p8r-x3mc-p8w7, via `ajv`), and `brace-expansion` on both major lines for GHSA-rgw5-rvv9-x895. **The lesson worth keeping is the mistake made on the way.** The first attempt pinned `brace-expansion@1: ">=1.1.18"`, which looks obviously right and is not: an override *target* is a range resolved against the whole registry, and `>=1.1.18` has no upper bound, so pnpm resolved it to the newest version in existence. GHSA-mh99-v99m-4gvg was accepted on 2026-07-31 with the reason "no 1.x patch exists"; 1.1.18 shipped one, so the same override that fixed the new advisory closed the accepted one too. An accepted advisory is a standing debt with a review date, and this one turned out to be payable — re-checking for a patch before renewing an exception is the habit that found it. Verified: web + CMS builds, both typechecks, lint, four guards, 154 unit tests, 57/57 `CI=1` e2e. (→ pnpm-workspace.yaml, pnpm-lock.yaml)

## ADR-035 (2026-08-04): Gate Payload's schema push on the database, not on NODE_ENV (P1.6.5c)
Context: found while removing the legacy `dev` migration row — a local `payload run` printed *"Pulling schema from database…"*, which is the schema-**push** machinery, against production. The rule was `push: process.env.NODE_ENV !== "production"`, written to mean "push is a local-development convenience where a mistake costs nothing" (ADR-029). The reasoning had a hole large enough to repeat the ADR-029 outage: **there is no local database in this project.** `apps/cms/.env.local` holds the production connection string — that is precisely why `migrate-on-deploy.mjs` was gated on `VERCEL_ENV`, and why the handover warns that any local migrate touches live data. So every local `payload run` — `set-user-roles`, the article importer, any one-off script — had `NODE_ENV` unset, push enabled, and a live connection: Payload would silently reconcile production's schema to whatever the working tree's collections happened to say. Nothing had gone wrong yet only because the tree matched. Decision: gate on the connection target instead — `push: isLocalDatabase(process.env.DATABASE_URL)`, true only for `localhost`/`127.0.0.1`/`::1`/`host.docker.internal`. The helper **fails closed**: an unset, malformed or unrecognised URL returns false, so "we could not tell" disables push rather than authorising an unattended schema change on someone's production data. This is strictly better than the env-var approach ADR-029 rejected *and* than `NODE_ENV`, because it keys off the thing that actually determines the blast radius rather than a proxy for it. Consequence: push is now effectively off everywhere until someone runs a genuinely local Postgres, which is the correct posture — schema changes ship as migrations (ADR-029), and the convenience push was preserving had no safe place to happen. The general lesson: **an environment flag describes intent; the connection string describes consequences — guard on consequences.** (→ apps/cms/src/payload.config.ts)

## ADR-038 (2026-08-05): FAQPage structured data, keyed off punctuation rather than a heading (P1.6.x)

## ADR-039 (2026-08-05): An untranslated locale must not be an indexable page (P1.6.15)
Context: checking what the 30 imported articles would do in search once published. The sitemap correctly picks up CMS content, but it emitted **all four locales for every document**, and Payload is configured with `fallback: true` — so `/ar/learn/meet-femio`, `/fr/…` and `/es/…` all return **200 with identical English content**, advertised in the sitemap and claiming hreflang alternates. Publishing the 30 articles would have created **120 URLs of which 90 were duplicate English** presented as Arabic, French and Spanish pages. On a YMYL health site, where Google is strictest about thin and duplicated content, that is a self-inflicted quality signal — and the failure is silent, because every page returns 200 and looks fine. Decision: **ask the CMS which locales a document is genuinely written in and treat that as the truth.** `fallback-locale=none` is the honest question — it returns a null title where no translation exists — so `availableLocales(collection, slug)` reports the real set. The fallback stays on for the same reason. `x-default` needed care: it now points at the default locale when that exists and otherwise at the first available one, because an `x-default` aimed at a page we do not have is worse than omitting it. Six unit tests cover the alternates logic, including the empty-set case (falls back to all locales rather than emitting a broken cluster) and the self-referencing canonical on an untranslated page. Cost: one CMS request per locale per document in the sitemap, on the same five-minute cache as every other read. (→ apps/web/src/lib/cms/client.ts, lib/seo/metadata.ts, app/sitemap.ts, both content routes)

## ADR-040 (2026-08-05): The connection pool is the CMS's real constraint — and a CMS outage must not 404 a live article (P1.6.16)
Context: publishing the imported batch took the CMS API to **500 twice**, both times `(EMAXCONNSESSION) max clients reached in session mode — max clients are limited to pool_size: 15`. Two contributing causes, one mine. **Mine:** `availableLocales` (ADR-039) asked the CMS per *document*, so the sitemap made ~4 requests per article — around 120 per regeneration once 30 articles existed — each a serverless invocation holding a Postgres connection. A change whose entire purpose was a cleaner sitemap took the API down. Fixed by asking per *locale* instead: `translatedSlugs` answers the same question in four requests regardless of how many articles exist. The lesson is dull and worth writing anyway — *a loop over documents that makes a network call per document is an outage waiting for the collection to grow*, and it looked perfectly reasonable at 1 article. **Structural:** `DATABASE_URL` points at Supabase's **session-mode** pooler (port 5432), which dedicates one Postgres connection per client for that client's whole life and is capped at 15, shared between the CMS's functions, the web app's functions, and any local script. That is the wrong pooling mode for serverless and it will keep biting; the fix is the transaction-mode pooler (port 6543), recorded as an owner task since it is a Vercel env change. **Second decision, from watching the outage:** while the CMS was down, `getContentBySlug` returned null and the article routes called `notFound()` — so every published article answered **404**. That is the one failure mode search engines punish, because a 404 invites deindexing while a 5xx is understood as transient and retried. `query` now distinguishes "the CMS answered and has no such document" from "the CMS is unreachable", and the single-document fetch throws `CmsUnavailableError` on the latter so the route answers 5xx. Graceful degradation is right for a list or a nav; it is wrong for the canonical URL of a published page, where being quietly absent is worse than being loudly broken. (→ apps/web/src/lib/cms/client.ts, app/sitemap.ts)

## ADR-041 (2026-08-05): Pregnancy gets a real dashboard, not cycle tools and an apology (P1.13b, owner direction)

## ADR-042 (2026-08-05): Menopause mode reports the count and stops short of the conclusion (P1.13c)
Context: the last of the four onboarding modes still landing on a "coming soon" card. The design question is narrower and sharper than pregnancy's: the clinical convention for menopause is twelve consecutive months without a period **with no other cause**, and that final clause is the whole problem. Pregnancy, thyroid disease, some medicines and several other causes also stop periods, and deciding which applies is diagnosis — outside what Femio is (product rule 1) and, on a tracker with no access to bloods or history, frequently wrong. A screen that counted to twelve and announced menopause would be both a regulatory problem and a straightforwardly bad answer. Decision: **report the arithmetic, name the convention as a convention, and route to a conversation.** The panel shows months since the last logged period, states what clinicians usually mean by twelve months, and says plainly that this is a count of dates she entered rather than an assessment — naming the other causes explicitly, because "see your clinician" is much easier to act on when a reader knows *what for*. Three supporting choices: **(a)** months are counted by **calendar**, not days ÷ 30 — "six months" should mean on the screen what it means on her calendar, and the 30-day approximation drifts by days a year (tested against the awkward cases: 31 Jan → 28 Feb has not completed a month). **(b)** Cycle **variability** is surfaced rather than an average, because in perimenopause the variation is the informative part and a confident single predicted date is precisely what this stage cannot support (product rule 3); it reuses `predictNextPeriod`'s `spread > 9` threshold, since two screens disagreeing about whether her cycles are regular is a bug she has no way to resolve. **(c)** The symptom list is filtered to the menopause-associated subset of the **existing** taxonomy — `hotFlashes`, `insomnia`, `brainFog`, `moodSwings`, `jointPain` and the rest were already there, so nothing new needed logging or translating. Fourteen unit tests, weighted toward the calendar-month edges and the "returns null rather than a number derived from nothing" cases. All four onboarding modes now have a real dashboard. (→ apps/web/src/lib/menopause/, components/menopause/, dashboard/page.tsx)

## ADR-043 (2026-08-05): A pregnancy has to be endable, and the default after it must not be a fresh form (P1.13d)
Context: P1.13b shipped a pregnancy dashboard with no way out of it. The schema had anticipated this — `pregnancy.status` accepts `completed`, `loss` and `ended`, and the table holds a row per pregnancy precisely because a life spans several — but nothing in the UI ever set it. Two failure modes followed, and the second is the one that matters: the week counter simply kept running past term; and once the record aged past plausibility, `pregnancyProgress` returned null and the panel fell back to its empty state, which is **"Set up your pregnancy"**. So a person who had just had a loss was shown either a running count of a pregnancy she no longer had, or a cheerful invitation to start another. Neither is a neutral default, and the cost of getting it wrong is entirely hers. Decision: an `EndPregnancy` control with three plainly-named outcomes, and a dashboard that reads the most recent pregnancy **regardless of status** so that "no active row" can never silently mean "start again". The design choices are all about not making a bad day worse. The trigger is a quiet link, not a button competing with the week count. Confirmation is **one** step — being asked twice to confirm a loss is its own small cruelty, and the action is reversible in the sense that nothing is destroyed. The outcomes are named without euphemism ("I lost my pregnancy"), because a euphemism here reads as discomfort with her situation. Nothing is deleted: the row is kept with its status so history stays intact and export/delete continue to work like any other data. And the closing copy differs by outcome — congratulations where that fits, plain acknowledgement and an explicit promise that Femio will stop showing week counts where it does not. Deliberately **not** built: a postpartum mode. `completed` says honestly that those tools do not exist yet rather than pretending; inventing a half-postpartum experience on the way past would be worse than naming the gap. (→ apps/web/src/components/pregnancy/end-pregnancy.tsx, pregnancy-panel.tsx, dashboard/page.tsx)

## ADR-044 (2026-08-05): The connection cap was never the problem — the per-instance pool size was (P1.6.17)
Context: ADR-040 identified `EMAXCONNSESSION` (pool_size 15) as structural and recorded "switch to the transaction-mode pooler (port 6543)" as a two-minute owner task. **That advice was wrong on both halves, and the owner asking for a step-by-step is what surfaced it.** First, `docs/runbooks/OWNER_MANUAL_TASKS.md` already records port 6543 as a *failed* attempt here: Supabase's transaction pooler does not support prepared statements, and Payload fails against it. Recommending it would have cost an outage and a rollback. Second, and the actual cause: the adapter passed `pool: { connectionString, ssl }` with **no `max`**, so node-postgres applied its default of **10 connections per instance**. That default is right for a long-lived server and badly wrong for serverless against a session-mode pooler, where every client holds a dedicated Postgres connection for its whole life. Two warm CMS instances could claim 20 of a 15-slot pool between them — which is precisely how publishing 30 articles took the API down twice, and why it recovered on its own each time as instances went cold. Decision: `max: 1`, plus a 10s idle timeout so a slot is handed back quickly and a 10s connect timeout so an exhausted pool fails fast instead of hanging a function. One is the correct number rather than a cautious guess: a Node serverless function serves a single request at a time, so a second connection per instance can only ever sit idle holding a slot someone else needs. **Fix the demand, not the cap.** This removes the owner task entirely rather than reassigning it, which matters given the standing direction to reduce manual work — and it is the second time today that a change whose stated purpose was tidiness turned out to be the thing that would have broken production, the first being the per-document sitemap query in ADR-040. The general lesson: *a library default is a decision made for a deployment model that may not be yours, and the ones that never surface in development are the expensive kind.* (→ apps/cms/src/payload.config.ts)

## ADR-045 (2026-08-06): Slugs stay English across all four locales (P1.6.9, owner decision)
Context: `docs/16` §5 specified translated slugs; the CMS has always had one shared, non-localized `slug` field (`unique: true`) while `title` and the body are localized. The owner asked directly whether to keep slugs English everywhere, noting he does not want unnecessary complexity. Decision: **keep them English.** The reasoning is not only simplicity. **(a) The benefit is currently zero and later small.** Nothing is translated yet, so a localized slug would capture no in-language traffic today; and once translations exist, hreflang correctness (already shipped, ADR-039), the translated `title`/`meta_description`, and the body itself carry nearly all the ranking weight — the slug is a tiebreaker, not a lever. **(b) Arabic slugs percent-encode.** `تكيس-المبايض` becomes an unreadable `%D8%AA…` string the moment it is copied, shared or pasted into a messaging app, which undoes most of the readability argument that justifies localized slugs in the first place. **(c) The cost is four systems, not one field.** Localizing the slug means per-locale uniqueness, a redirect map, internal-link resolution that varies by locale, and changes to the importer, the content guard and the sitemap. **(d) It is not a one-way door**, which is what makes deferring safe rather than merely cheap: if a specific Arabic or French page later underperforms, an optional per-document localized slug can be added for *that* page without converting the set. The expensive, irreversible-feeling version is committing to all of them up front — which is precisely what the original spec asked for and what is being declined. Consequence: `docs/16` §5 is superseded on this point and should not be read as pending work. The condition that would reopen it: evidence from Search Console that in-language pages are losing to competitors on queries where the URL is visibly part of the snippet — a real signal, not a hypothetical, and available only after translations ship. (→ apps/cms/src/collections/factory.ts — unchanged, this ratifies the existing shape)

## ADR-046 (2026-08-06): `max: 1` deadlocked the CMS, and a sitemap must fail loudly rather than ship empty (P1.6.18)
Context: the owner reported the sitemap "not readable". It was worse than that — it contained **60 URLs, all static pages, and zero of the 31 published articles**, and that file had already been submitted to Google Search Console. Investigating produced two findings and one correction of my own work from an hour earlier. **(a) `max: 1` was wrong and took the CMS down.** ADR-044 set the Postgres pool to one connection per instance on the reasoning that "a Node serverless function serves one request at a time". That is true of *requests* and irrelevant to *connections*: Payload issues several queries within a single request — a find alongside a count, and a transaction that holds its connection while issuing more — so one connection deadlocks until `connectionTimeoutMillis` fires and **every** request 500s. `max: 3` leaves room for intra-request parallelism while still capping fan-out far below the 15-slot session pool. The correction is worth stating plainly because ADR-044 argued its number was "correct rather than cautious"; the confidence was misplaced, and the check that would have caught it was hitting the deployed API afterwards, which ADR-029 already prescribes. **(b) The sitemap silently degraded.** With the CMS 500ing during generation, `listContent` returned `[]`, the route emitted static pages only, and Next cached that **200** for an hour. Nothing failed. But absence from a sitemap is read by a crawler as a signal about the missing pages, so a quietly-truncated sitemap is worse than none — the same shape as the outage-becomes-404 bug fixed in ADR-040, which I fixed for article routes and did not fix here. The sitemap's content queries now use `throwOnFailure`, so a CMS failure yields a 5xx that Google simply retries. **(c) A verification lesson.** My earlier "proof" that `fallback-locale=none` worked used `d.get('docs', [])`, which returned `[]` from an *error* response and told me what I expected rather than what was true. Re-tested properly: the parameter is correct — Arabic returns `title: null`, English returns titles. **The check that would actually have caught this looks at production**, since `NEXT_PUBLIC_CMS_URL` is unset in CI and CI's own sitemap correctly has no articles: `scripts/seo/sitemap-check.mjs` runs in the weekly job and asserts articles present, no untranslated locales, and no excluded pages. It was written against the broken sitemap and observed to fail before being trusted. ## ADR-047 (2026-08-06): In pregnancy, the symptoms that matter most are not log entries (P1.13d)
Context: `/track` offered the cycle symptom set to everyone, so a pregnant user was asked about period cramps and had nowhere to record vomiting, swelling or reduced movements — and was still shown a next-period prediction and a fertile-window calendar overlay. The vocabulary gap is the obvious problem and the smaller one. The real issue: **the symptoms that matter most in pregnancy are not log entries at all.** Reduced fetal movement, heavy bleeding, a severe headache with vision changes — recording those quietly and returning the user to a list of chips would be the app filing away the exact thing it should be interrupting for. Decision: a pregnancy-specific logger where urgent symptoms are separated from everyday ones and selecting one replaces the quiet save with guidance to contact care. **Two tiers, not one:** an emergency list (emergency services now) and a same-day list (contact your maternity team), because collapsing them means either under-reacting to bleeding or over-reacting to heartburn, and an app that shouts "emergency" at everything teaches people to ignore it. **The tiers mirror `pregnancy-warning-signs.md` item for item** — if the app and the published article disagree about what is an emergency, the reader cannot tell which is right, and she is more likely to be looking at the app. **The entry is still saved**, and the button says so ("Save and get help", "saving does not contact anyone"): someone who logs bleeding and then phones her midwife should find it in her history, and a record she can show is often the useful thing. Refusing to save would also teach her not to log the serious ones. Also removed from pregnancy mode: the next-period prediction and the cycle calendar's predicted-period and fertile-window bands, for the same reason the dashboard drops them (ADR-041) — they are not merely irrelevant but actively misleading. Twelve tests on the tier logic, including that the *highest* urgency wins when both are selected (showing both buries the serious one), that the tiers are disjoint (an overlap would make classification depend on lookup order), that urgent keys never leak into the everyday groups, and that self-harm is classified as an emergency rather than a mood entry. (→ apps/web/src/lib/pregnancy/symptoms.ts, components/pregnancy/log-pregnancy-symptoms.tsx, app/[locale]/(app)/track/page.tsx)

## ADR-048 (2026-08-06): The tracker ships as a package, not a second copy — and the rule is enforced, not written down (P4.0)
Context: the audit (`docs/19` §2) found every tracker screen was a `force-dynamic` server component, so the Phase 4 Capacitor plan could not run, and offered three options of which `output: "export"` was called "effectively a rewrite". The Step 1 spike (`docs/20`) disproved that: the export works. It produced 41 pages across four locales with RTL intact and no server runtime, including a client-rendered `/dashboard` doing a browser-Supabase read and a `/track` carrying the real `LogSymptoms`. Decision, in three parts. **(a) Target shape: two thin Next apps over shared workspace packages** — `packages/core` for the ten genuinely shared modules, `packages/tracker` for the tracker screens with route files reduced to one-line re-exports, `apps/web` server-rendered for SEO, `apps/native` static-exported. Webview-onto-live-URL is rejected outright, not deferred. **(b) The split is deliberately NOT executed now.** There are no users and no store presence, so a Phase 4 packaging change earns nothing today; what matters is only that Phase 2 must not make it more expensive. Once the screens are client-rendered and server-free the move is mechanical; after twenty more server components it is not. **(c) Therefore the deliverable is a constraint made enforceable, not a plan.** `pnpm native-readiness-lint` fails on server-side Supabase reads, `force-dynamic`, Server Actions and `searchParams` props anywhere in the tracker path. It is a **ratchet, not a gate**: the 13 current violations across 6 files are baselined, and it fails both on a new violation *and* on a stale baseline entry, so the list can only shrink and can never quietly over-claim. It was watched failing in both directions before being trusted — and it immediately caught an error in `docs/20`, where I had written that `await searchParams` affected one file. It affects three; the grep behind that claim had been run after I stubbed two of them, so it searched the tree I had already modified rather than the one I was describing. The general lesson, and the reason the guard exists rather than a paragraph asking people to be careful: **the native build fails quietly** — middleware is silently disabled under export, taking locale routing and Supabase session refresh with it — so nothing except a guard pointed at the source would have told us it had rotted. ## ADR-049 (2026-08-06): The kick counter is a pattern log with no pass mark, because the safe-looking version is the dangerous one (P2.2)
Context: P2.2 names a "kick counter", and the obvious implementation is the one every competitor ships — count to ten, show a progress ring, congratulate her on reaching it. **That version is unsafe, and Femio's own published guidance already says so.** `docs/content/articles/pregnancy-warning-signs.md`, which has been through review, states: *"There is no single normal number for everyone. Your baby's change from usual matters"* and, to "Should reduced movement wait until tomorrow?", answers *"No."* A count-to-ten target contradicts both. The harm runs in the dangerous direction: reaching ten is read as "all is well", so the woman whose baby is moving much less than usual gets **false reassurance from the app and delays calling** — and formal counting protocols did not reduce stillbirth when trialled, which is why RCOG/NHS guidance moved to pattern-awareness. It is also product rule 1: deciding that a pattern is fine is a clinical conclusion, and Femio does not draw them. Decision: a **movement pattern log**. Three properties, each defended in code. **(a) No verdict exists anywhere in the stack.** The migration has no `result`/`normal`/`passed`/`target` column — a schema that can hold a verdict will eventually render one — and a unit test asserts the comparison function exposes no such field. What it computes is minutes-per-movement and how the latest session compares to the **median** of her own previous ones. Median, not mean, specifically so one very long session (she got distracted, she put the phone down) cannot drag the baseline up and make a genuinely slow later session look normal — that would suppress the exact signal this exists to surface. **(b) The maternity-contact route is never gated.** It renders above the counter and is present before, during and after a session, saying not to wait for the count to finish. An app that says "finish counting first" would be actively harmful given the published answer is *no*. The 1.5x "slower than usual" prompt is a display threshold for when to *suggest* calling, never a diagnostic one, and it is deliberately biased to prompt too often — a false prompt costs a phone call. **(c) An unfinished session always saves.** `movement_count` is nullable on purpose: the woman who stops counting because she is worried and is going to phone is the person this feature is for, and her record should show that she stopped. `minutesPerMovement` returns null rather than a number when zero movements were recorded, so nothing can divide a short duration by zero felt movements and produce a small, reassuring-looking figure. Also: the table joins the GDPR export list and cascades on profile delete, and the offline queue accepts it, because a hospital corridor is exactly where signal drops and exactly where someone may be counting. **What a future session must not do:** add a target number, a progress ring, or an "everything looks normal" state. That would look like completing the feature and would be the single most harmful change available in this app. (→ supabase/migrations/0007_fetal_movement_sessions.sql, apps/web/src/lib/pregnancy/movements.ts, components/pregnancy/movement-counter.tsx)

## ADR-054 (2026-08-07): The wizard becomes a real radio group, and two silent failure modes surface — an unmapped token and a Tailwind cache that ignores it (P1.28.5)

## ADR-055 (2026-08-07): Reduced motion is enforced globally, not per component — and press feedback belongs on the Button, not on whichever control someone remembered (P1.28.6)
Context: `femio.tokens.css` has shipped `--dur-instant/fast/base/slow` and four easing curves including `--ease-spring` since the token system was built, and until this workstream nothing used them. The three preceding subtasks started to, but only where they touched — which is exactly the failure mode worth designing out. Decision, three parts. **(a) `prefers-reduced-motion` is a global rule in `globals.css`, not a `motion-safe:` convention.** Tailwind's variant works, but it only protects the places someone remembered to type it, and the twelve `animate-pulse` loading skeletons predate the convention entirely — a user who has asked her OS for less motion was getting a pulsing skeleton on every screen that loads data. ## ADR-057 (2026-08-07): The persona resolver, built so that it cannot restrict anything — and honest that it covers 15 personas, not 73 (P1.27.4)
Context: ~73 personas were specified in `docs/personas/` with a scoring resolver designed in `docs/09` §5, and the app mapped four onboarding modes to four hardcoded ids. The schema was never the obstacle — `persona_state` has carried `modifiers[]`, `emotional_context[]`, `confidence` and `clock_json` since v1, all unused. This is the scoring layer. Decision, four parts. **(a) The result type cannot express restriction, and a test enforces the shape.** `Resolution` is `{personaId, track, modifiers[], emotionalContext[], confidence, runnerUp}` — no `hidden`, `blocked`, `disabled` or `available`, and a test asserts the exact key set so one cannot be added quietly. Invariant 1 of docs/09 is "personalize, never restrict", and the difference between a rule someone remembers and a type that cannot represent the violation is the difference between this holding for a year and not. Same reasoning that kept a `result` column off the movement-log schema (ADR-049): if a future feature genuinely needs to hide something, that is a product decision with its own ADR, not a field quietly added here. **(b) Z1 is an answer, not a failure, and the resolver never applies a persona on its own authority.** Two conditions force Z1: a confidence below `CONFIDENCE_THRESHOLD` (0.6), and a top score within `AMBIGUITY_MARGIN` (0.08) of the runner-up — docs/09 §5's "blend the two nearest rather than committing". In both cases the runner-up is returned, so P1.27.5 can *offer* ("Want me to tailor Femio for X? You can undo this anytime"). Confidence is additionally scaled by **signal coverage**: a persona resolved from one populated signal out of six is a guess wearing a score, so thin evidence suppresses confidence even when the one signal matches perfectly. **(c) D3 and D4 are separated by construction.** docs/09 §8 rule 3 is explicit that gestational diabetes (resolves postpartum, one-off OGTT) and pre-existing diabetes (lifelong, ongoing E4) must never be conflated, and the only thing distinguishing them is whether diabetes was recorded before the pregnancy — so that is its own signal field and both personas gate on it, meaning exactly one can ever be a candidate. Scoring cannot get it wrong because scoring never sees both. Tested behaviourally *and* structurally, and both tests were watched failing against a deliberately conflated build. Modifiers resolve independently of which persona wins, because docs/09 §8 makes them composable layers — someone in D1 with a thyroid condition still gets the thyroid layer, and `prior_loss` marks emotional context wherever it appears, because invariant 7 suppresses celebratory content everywhere rather than in one persona. **(d) Fifteen rules, and the file says why not seventy-three.** A persona is listed only once Femio records the signals it keys on. Most of the taxonomy keys on labs, BBT/OPK series, partner semen analysis and validated screeners that no screen collects (P2.1, P2.7); writing rules for those would create branches that can never fire and a resolver that looks finished while quietly never resolving half its range. `PersonaSignals` is likewise restricted to data we actually hold, for the same reason. Each absent group is noted in place so the next session extends rather than rediscovers. **What is deliberately not done:** nothing reads this yet. Deriving signals from Supabase and writing to `persona_state` is tracked as **P1.27.4a**, and until it lands the app still uses the four hardcoded ids — the resolver is built, tested and unused, which is stated in the TODO rather than implied. ## ADR-065 (2026-08-16): E3 resolves from what she said, not from her EPDS score — and E5 is not a persona at all (R2.5f)
Context: Track E had three specs left unbuilt — E3 (postpartum mood), E4 (follow-up after a complicated pregnancy), E5 (contraception and return of fertility) and E7 (thyroiditis watch). E4 and E7 were mechanical: the postpartum triage already asks about `gestational_diabetes`, `diabetes`, `hypertension`, `pre_eclampsia` and `thyroid`, so each has a signal and a gate. **The other two forced decisions that a future session could reverse by accident, which is what puts them here rather than in a commit message.** Decision. **(a) E3 is gated on the `depression_anxiety` code she selected, never on a screener total.** E3 §A describes her arriving "when an EPDS check-in came back elevated", and `screener_results` has held EPDS totals since P2.7, so wiring the score to the resolver was available and would have read as the obvious implementation. It is the wrong one: reconfiguring a woman's app because a questionnaire crossed a line is Femio deciding she has a condition, which is product rule 1, and it is the same line P2.7 already refused to cross at the point of *scoring* — no band, no label, no cut-off in the module. A score that cannot be allowed to produce the sentence "your symptoms are severe" cannot be allowed to silently produce a mood-shaped app either. The self-reported code is her own statement about her own history, which is what every other persona in the resolver keys on. **Consequence, stated plainly:** a woman who develops postpartum depression *after* onboarding and never re-answers the triage will not resolve to E3. She still gets E1 with the EPDS on it and the crisis route on item 10, which is the part that matters; the persona is tone and emphasis, and buying it with an inference would cost more than it is worth. Re-answering the triage (P1.27.3) is the intended route, and an *offer* on a sustained mood trend — offered, never applied, like every other transition — is the honest version of the score idea if it is ever wanted. **(b) E5 is not built as a persona, and its substance ships as content on E1.** Its spec's success criterion is "no surprise: she knows fertility can precede the first period" — which is true of *everyone* in Track E, not of a distinct group. Femio holds no signal that separates the woman thinking about contraception from the woman who is not, and inventing one (weeks postpartum, "not TTC") would have produced a record that outscored E1 for almost every postpartum account, making the general persona vestigial to no benefit. So the P2.3c articles carry it — `contraception-after-birth` and `periods-after-birth`, both foregrounded from E1 — and E5's LAM-criteria awareness prompt stays queued as a *module*, not a persona. **(c) E4 is ordered ahead of E7, and E3 ahead of both**, because `docs/09` §8 rule 2 gives the hero to the most acute: the E4 schedule is time-critical (the 72-hour and 7–10-day blood-pressure checks, the 4–12 week glucose test), postpartum thyroiditis is a watch across a year, and postpartum mood is the tier this product treats as its highest sensitivity. **(d) E1 gained `conditions.length === 0` as a signal — the fourth appearance of the same trap.** Without it E1 and E7 both scored 1.0 for a woman who had reported her thyroid, E1 won on rule order, and the condition she had told us about changed nothing at all. ## ADR-066

**Femio names the cycle phases — but only when her own cycles support it.**

Date: 2026-08-21 · Owner: Khaled · Status: accepted · Supersedes the inline refusal in
`cycle-experience.tsx` · Related: ADR-042, ADR-049, `docs/25` §5a, `docs/26` §7, `docs/27` phase 1

### Context

Two prior decisions pointed the other way, and both were reasoned.

`cycle-experience.tsx` shipped a "Where you are" card that gives a cycle **day** and deliberately
no phase name, with the comment: *"naming a phase from cycle length alone is an inference about
her hormones."* That is a fair objection. For an anovulatory cycle — PCOS being the obvious case,
and one Femio explicitly serves — calling days 12–16 "ovulatory" is not an approximation, it is
wrong, and it is wrong in the direction of implying fertility.

Against that: the design tokens have carried `--phase-menstrual`, `--phase-follicular`,
`--phase-ovulatory` and `--phase-luteal` since the token work, unused. And the competitive
research behind `docs/26` §7 is unambiguous that apps which explain the phases deliver
dramatically more value than apps which only predict when bleeding starts. Femio was doing only
the second, in prose, on a dashboard measuring 844px.

So the choice was not "honest vs useful". It was whether the honest version of useful exists.

### Decision

It does, and it is a **conditional** naming rule:

1. **Phases are named only when her cycles are regular enough to support the estimate.**
   `lib/cycle/phases.ts` returns `null` for `irregular`, and for any cycle shorter than 21 days
   where the backwards estimate would collide with the bleeding days. `null` is rendered as
   "still learning your pattern", never as a default phase.
2. **Ovulation is estimated backwards** — `cycleLength - 14` — never assumed to be day 14. Day 14
   is true only of a 28-day cycle and is the most common error in this category; for a 32-day
   cycle it puts the window four days early.
3. **The ovulatory phase is a window, never a day.** A single highlighted day is the shape read
   as a fertility guarantee, and product rule 1 keeps Femio out of contraception entirely.
4. **Framing is "typical for a cycle your length", never "your hormones".** Femio describes a
   pattern that has already happened. It does not report an endocrine state it cannot measure.

The original objection is therefore preserved rather than overridden: Femio still refuses to
infer a phase from cycle length alone *when the length does not support it*. What changes is that
it no longer refuses when it does.

### The visual is a strip, not a ring

`docs/25` §5a rejects rings and circular progress outright — a ring implies a target and a
completion, and a cycle is not a task you finish (ADR-049, ADR-042). That decision stands
untouched. This work was drafted as a ring, caught against §5a, and rebuilt as the **strip**
§5a already prescribes: horizontal, phases as segments, soft edges, a today marker. Same
glance-value, no completion metaphor, mirrors in RTL for free.

Recording that near-miss deliberately: the ring was half-built before the rejection was found,
which is exactly the "reversed by accident" failure the ADR bar exists to catch.

### Consequences

- Phase education (`docs/27` phase 3.1) becomes buildable, and is the differentiator the research
  identified.
- The four phase tokens are used for the first time.
- Irregular-cycle users get a visibly *different* and better-reasoned experience than at Flo or
  Clue, where neither handles them well — turning the constraint into the positioning.
- `LUTEAL_DAYS`, `OVULATORY_SPAN` and `DEFAULT_PERIOD_DAYS` carry `[NEEDS SOURCE]` and must have
  Tier-1 citations before any of this reaches user-visible educational copy.

## ADR-068

**A partner sees a curated server-rendered view, and the v1 RLS policy that would have shown him
her scope is removed.**

Date: 2026-08-23 · Owner: Khaled · Status: accepted · Related: `docs/compliance/PARTNER_SHARING_DESIGN.md`,
`DPIA.md` §3–§4, ADR-060, migration `0011_partner_sharing.sql`, `docs/27` phase 4.5

### Context

Partner sharing was scope-approved on 2026-08-23 with a design whose three load-bearing decisions
are not the checkboxes: revocation must be **silent**, a withheld category must be **invisible
rather than marked withheld**, and the highest-harm categories must have **no checkbox at all**.
Building it turned two of those from copy into architecture, and each cut against something the
repo already did.

### Decision 1 — the v1 `partner_links` SELECT policy is dropped

Schema v1 shipped `partner_links_select_involved`, which let **the recipient read the row naming
him**, with the stated intent "so they know their scope". Under the design that policy is the
single worst thing in the feature: the row carries `scope_json`, which is *the list of what she
chose to conceal*, and `revoked_at`, which makes her revocation observable. It is §2 and §3 of
the design broken by one line of SQL written before either risk had a name.

It is replaced by an owner-only policy. The recipient now selects nothing at all; everything he
sees arrives through a curated function.

**Recording this because it is the accident-reversible case.** A future session reading
`partner_links` with no recipient policy will see an omission and be tempted to add one back. It
is not an omission. It is the feature.

### Decision 2 — `partner-view` holds the service role, and `experience` still must not

`experience`'s header states the principle plainly: no service-role key, the caller's own JWT,
RLS stays the security boundary. `partner-view` breaks it, deliberately and in exactly one place.

The forcing case is a partner granted `nextPeriod` and not `cycleDates`. He is entitled to a
predicted window and not to the start dates it is derived from — and there is nowhere in his
browser that can hold that distinction, because whatever the client is sent, the client's owner
can read. The three alternatives were each worse:

- **Return the starts and filter client-side** — the leak the design exists to prevent.
- **Derive the window in PL/pgSQL** — a third implementation of cycle prediction, bound by no
  golden fixture, free to disagree with both clients about a woman's body.
- **Refuse `nextPeriod` without `cycleDates`** — granularity removed to protect a boundary, which
  is the opposite of the point.

So: one function, one privileged call (`partner_shared_rows`), and the recipient id passed as an
argument after being proved against his own JWT with the anon client first. The service key never
touches a table and never sees an id the caller did not prove. `experience` is unchanged and the
principle still holds everywhere it can.

### Decision 3 — the never-shareable class is a database constraint, not a UI absence

The design says the protection *is* the missing checkbox. A missing checkbox is a UI, and a UI is
one refactor from changing, so `partner_links.scope_json` now carries a CHECK that every key names
a shareable category. An insert naming `screenerResults` is rejected by Postgres whatever the
client believes it is doing. `ShareCategory` cannot express those three ids either, so there is no
type that could carry one to the database in the first place.

### Consequences

- `partner_links` is the seventh v1 table to hold real data, and it is reused rather than joined by
  a second `partner_shares` table — the house pattern is one revocable ledger, not two.
- Grants are time-boxed: 14 days for an unredeemed invite code, six months from redemption.
- Verified end-to-end against the deployed project on 2026-08-23 with three real anonymous
  accounts and the publishable key only — 20 assertions, including that a withheld category is
  absent from the payload rather than empty, that a revoked share returns byte-identical JSON to a
  stranger's, and that an unknown age is treated as a minor. The accounts were deleted afterwards.
- **Not yet cleared for launch**, and code was never the gate: `docs/13` §5 needs a disclosures
  section and the Art. 9(2)(a) wording needs DPO sign-off. Femio has no DPO appointed, which is a
  P0.12 dependency.

## ADR-069

**Partner sharing is cleared for the closed beta and not for public launch; the hero keeps its
gradient; Arabic renders Western digits.**

Date: 2026-08-23 · Owner: Khaled · Status: accepted · Related: ADR-068, ADR-051, `docs/13` §5b,
`DPIA.md` §5–6, `docs/25` §5a, R3.5.2, B12

Three owner decisions taken in one pass. The first needed research and is the substance of this
ADR; the other two are recorded because both had been raised as open questions and a future
session would otherwise re-open them.

### 1. Partner sharing — cleared for the beta, not for the public

**The question.** `PARTNER_SHARING_DESIGN.md` set two launch gates: a disclosures section in
`docs/13` §5, and **DPO sign-off** on the Art. 9(2)(a) wording. Femio has no DPO, and appointing
one is inside P0.12, which is deferred until the first real user. Taken literally that is circular:
the feature cannot launch until a DPO exists, a DPO does not arrive until there are users, and
users cannot arrive without something to use.

**What the research actually says.** Art. 37(1)(b)–(c) makes a DPO mandatory where core activities
consist of *large-scale* processing of special categories of data. Femio's core activity is health
data, so at scale this is unambiguous — a public Femio needs a DPO. **"Large scale" is not met by a
closed beta.** Recital 91 and WP29's DPO guidance (WP243) weigh the number of data subjects, the
volume, the duration and the geographic extent, and draw the line by contrasting an individual
practitioner's records with a hospital's. Twenty to fifty invited testers on an invite code is the
former. Art. 35(2) — *seek the advice of the DPO* — is likewise conditional on one having been
designated.

**So the DPO gate was mis-specified, not wrong.** What is required at *any* scale is: explicit
consent that names the recipient and the data, a DPIA (which exists), transparency under Art. 13,
and a record of the disclosure. Those are satisfiable now, and three of the four already were.

**Decision.** Partner sharing is cleared to ship **to the private beta**, subject to three
conditions, all of which are now met:

1. **`docs/13` §5b exists** — a disclosures table for third parties who are not processors, with
   partner sharing as its single entry, and the explicit rule that nothing may be disclosed to a
   non-processor that is not described there. Written this pass.
2. **The consent moment names the recipient.** It did not. 0011 shipped granular consent — she
   ticked seven categories individually — but the recipient was *whoever redeemed the code*, so at
   the moment she agreed there was no identified recipient to agree about. That is granular consent
   and not **explicit** consent, and it is the one substantive compliance gap the build had.
   Migration 0012 adds `recipient_label`: she names the person, in her own words, before she can
   create the invite. He never sees it and cannot set it — otherwise it becomes another field a
   coercive partner can ask her to change.
3. **The beta gate is on** (P0.12.5). Without it "private beta" is a claim rather than a fact, and
   the clearance above rests entirely on the population being invited rather than arriving.

**Not cleared for public launch**, and the gate there is unchanged in substance: P0.12 delivers the
entity, the DPO and a privacy policy in force, and `docs/13` §5b plus the Art. 9(2)(a) wording get
reviewed by that DPO as part of it. The scale argument that opens the beta closes at exactly the
point the beta ends.

**What is *not* claimed.** This is a reasoned engineering-and-compliance position, not legal
advice, and it is recorded so counsel can disagree with something specific rather than with a
vibe. The residual risks in `DPIA.md` §6 — retention after revocation, and whether the coercion
mitigations are sufficient in every jurisdiction — remain open and are unaffected by beta scale.

### 2. B12 — the in-app hero keeps its gradient

ADR-051 put the gradient hero into the dashboard as the fix for the "AI generated" verdict.
ADR-067 then established that `docs/25` §5a never contradicted it: the "never inside the signed-in
app" clause attaches to `--gradient-dawn`, the marketing gradient, not to `--gradient-hero-*`.
Owner direction confirms it: **the hero keeps its gradient.** No code changes; B12 closes; §5a is
not amended.

### 3. R3.5.2 — Arabic uses the same digits as English

Owner direction, verbatim in substance: *"arabic digits are same as english"*. Western digits
throughout, dates and numbers alike.

**This was already true and only by accident**, which is the part worth recording. Every literal in
`ar.json` uses Western digits, and both Node's ICU and Chromium resolve `ar` to the `latn`
numbering system — so `docs/26`'s "Arabic mixes Western and Arabic-Indic digits" no longer
reproduces. But nothing in Femio *asks* for `latn`; it is today's CLDR default. A future ICU
release flipping it would change every number a woman sees, with no code change and no failing
build, months from any cause anyone could connect it to.

So the decision is pinned by `apps/web/src/i18n/numbering.test.ts` rather than left to a default.
If it ever fails, the runtime changed its mind and the fix is to pass the `-u-nu-latn` extension
where we format — not to relax the test.

   own; a privacy tripwire (`scripts/analytics-lint.mjs`) fails the gate if either product gains an
   analytics, error-reporting, ads or database client, or if the release manifest asks for
   INTERNET. The Supabase project is to be paused and the CMS Vercel project deleted (owner).
3. **The calculators take dates from an interactive calendar**, not a native date field: tap the
   day, the result draws on the same grid, with the register's rules (six-day window ending on
   ovulation, no window outside 21–35 days, nine-day spread for "regular", local today, the
   mandated fertility sentence). The persona resolver and experience engine have no consumer and are
   removed with the tracker; the twin discipline continues through `fixtures/domain`.
4. **The app seals its record** (AES-GCM, key in the Android Keystore), serialises writes,
   quarantines an unreadable file instead of overwriting it, exports a passphrase-sealed backup she
   saves herself, offers a PIN lock, blocks Google backup and device transfer, and signs releases
   from a key outside git.
5. **One icon source** (`femio-app-icon-dusk.svg`) generates every surface; the logo is Dusk Bloom.

**Alternatives.** Keeping the tracker behind its flag "for sync later" (rejected: it cost a build
dependency on a restricted database and 72% of the catalogs for nothing). Keeping Payload as the

an editor one person uses). A native `<input type="date">` (rejected by the owner: the calendar
is the product's own language).

**Consequences.** `main` has no path back to accounts without a new ADR. The `ui_strings` human
edits, if any were never merged into the JSON catalogs, are lost when the project is paused unless
the owner exports them first (listed in `OWNER_ACTIONS.md`). FR/ES stay UI-only languages.

## ADR-073
**Date:** 2026-10-28 · **Status:** accepted · **Area:** app, dates

**Context.** The app shows the Hijri date beside the Gregorian one (rule 6). The pub packages
`hijri`, `jhijri` and `hijri_calendar` share one hand-typed Umm al-Qura table; sampled against
ICU (the calendar the phone's own locale data uses, Node 77.1 here) it was off by one day on 22
of 252 days, including whole months in 2029–2030. A wrong Hijri date on a fertility calendar is a
wrong fasting or prayer day for the reader.

**Decision.** No Hijri package. `scripts/domain/gen-hijri-fixture.mjs` asks ICU for the Umm
al-Qura month starts (1356–1500 AH) and writes `apps/mobile/lib/domain/hijri_months.g.dart` and
`fixtures/domain/hijri.json` (252 day cases + 24 Arabic month-line cases). `lib/domain/hijri.dart`
converts from that table; the website converts through `Intl.DateTimeFormat` with the
`islamic-umalqura` calendar. The fixture runs on both sides, so the two cannot drift silently.

**Alternatives.** A pub package (rejected: wrong by a day in sampled months, and nobody audits
its table). Computing the tabular (arithmetic) Hijri calendar (rejected: it is not what Saudi
Arabia or Egypt print; it drifts a day from Umm al-Qura regularly).

**Consequences.** Regenerate the table with the script when the ICU data changes (a Node
upgrade), and re-run both golden suites. Dates after 1500 AH (2077 CE) fall back to no Hijri
label rather than a guess. A browser's ICU may differ from Node on far-future days; the fixture
covers 2024–2035.

## ADR-074
**Date:** 2026-10-28 · **Status:** accepted · **Area:** web, i18n, Arabic

**Context.** Since 2026-08-22 (ADR-069, Western digits) `apps/web/src/i18n/request.ts` handed
next-intl `ar-u-nu-latn` as the Arabic locale so that every `Intl` call inherited the Latin
numbering system. next-intl 4 (in use since 2026-07-31) treats the config locale as the routing
locale: `Link`, `useRouter`, `usePathname` and `getLocale()` build every href from it. Every
internal link on every Arabic page of the live site therefore pointed at `/ar-u-nu-latn/…`, which
the middleware sent to `/en/ar-u-nu-latn/…`, a 404. Nothing caught it: the unit tests never
render a `Link`, the e2e suite navigates by URL, and the hand checks read pages without clicking.
Lighthouse run 3 surfaced it as three console 404s on each Arabic page.

**Decision.** The config locale is always one of `routing.locales`; the digits decision is pinned
by tests instead of by the locale tag. `request.test.ts` fails the gate if the config returns a
locale that is not a route; `numbering.test.ts` (already present) fails it the day Node resolves
bare `ar` to Arabic-Indic digits (CLDR 42+ resolves it to Latin digits, which is why the site
rendered Western digits before the tag and still does without it); `e2e/home.spec.ts` asserts that
every internal href on the Arabic home carries `/ar` and that a click lands. The calendar still
branches on the language part of the locale, which keeps it correct if a region ever rides along.

**Alternatives.** Wrapping `Link`/`useRouter` to pass the routing locale explicitly (rejected:
next-intl treats a `locale` prop as a locale switch, disables prefetch and writes the cookie on
every click). A custom prefix mapping `ar-u-nu-latn` → `/ar` in the routing config (rejected: the
locale would then leak into `lang=`, hreflang, the sitemap and every catalog lookup).

**Consequences.** On a browser older than CLDR 42 (Chrome 110 / Safari 16.4, early 2023) a
number formatted on the client (calendar aria-labels) may show Arabic-Indic digits; server-rendered
text is unaffected. Both are correct Arabic; the owner's preference for Western digits holds on
every current browser. Keep the rule in `docs/STATE.md` traps: never return a formatting tag as
the locale.

## ADR-075
**Date:** 2026-10-28 · **Status:** accepted 2026-10-28 (owner, in chat: "Accept ADR-075: the website may measure visits and carry ads after consent; the app stays untouched") · **Area:** privacy, website, growth, revenue

**Context.** Rule 4 ("the website collects nothing") and ADR-072 §2 (the privacy tripwire fails
the gate if either product gains an analytics, ads or database client) were written for a launch
with no revenue and no measurement beyond Play Console and Search Console. On 2026-10-28 the owner
asked for three things that touch that rule: (1) every visitor action measured "as a Shopify
store does", with a Google tag and a Meta pixel, with the least coding; (2) ads on the website's
articles and Learn pages, moderate and not annoying; (3) a premium subscription (about $1 a month
or $10 a year) that removes ads and unlocks premium content. The study's privacy promise is also
the wedge's main differentiator (`docs/32_STUDY/00_SYNTHESIS.md`), and Meta restricts what a
health-and-wellness domain may send through its pixel (domain-level "Core Setup" blocks custom
events and parameters; its terms forbid sending health information). Google requires a certified
consent platform for ads in the EEA/UK and Consent Mode v2 for its tags.

**Decision.** Split the two products cleanly:

1. **The app stays exactly as rule 4 says.** No analytics SDK, no ads SDK, no network permission,
   no account. The app's numbers come from Play Console (installs, retention, uninstalls, crashes,
   acquisition by UTM) which needs nothing inside the app. The app never shows ads; that is a
   store-listing sentence, not a loss.
2. **The website may measure visits and may carry ads, under consent and without health data.**
   Rule 4 becomes: "Her records never leave the phone. The website measures visits in aggregate,
   only after she agrees, and never records what she typed into a calculator." Concretely: one
   Google Tag Manager container; GA4 and the Meta Pixel load only from it; Consent Mode v2 with
   every signal defaulted to *denied*; a Google-certified consent banner (AdSense "Privacy &
   messaging" first, because it is free and certified; a paid CMP only if it proves insufficient);
   an event list that names pages, language, country, calculator *opened* and "Get the app"
   *clicked*, and never a date, a cycle length, a symptom, a result or a free-text field. The
   calculators keep computing in the browser and still send nothing of what she entered.
3. **Ads only on the website, only on content pages.** AdSense display units: one after the first
   section of an article and one at the end, none on the calculators' interactive area, none on
   help-now, legal, privacy or the app hand-off pages, none above the fold on mobile. Google's
   publisher policies on health content apply; the pages are education, not treatment, so they
   are eligible, but personalised ads on health pages are limited by Google itself.
4. **Premium lives in the app through Google Play Billing** (the only billing route open to an
   Egyptian seller besides PayPal/Paddle, and the only one with no server of ours). Target prices
   $0.99 a month and $9.99 a year, with Play's local prices in EGP and SAR; the per-country floors
   are read in Play Console when the subscription is created (not verified from documentation).
   Premium **adds** (exports for the doctor visit, printable reports, longer history views,
   extra themes, the in-depth guide series) and never removes a tool or an article (rule 2).
   Because the app has no ads and the website has no accounts, "premium removes ads" is not
   something the architecture can offer; the honest promise is "the app never shows ads".
5. **The tripwire changes deliberately, not by exception.** `scripts/analytics-lint.mjs` keeps
   failing the gate for the app and for any direct analytics/ads package in `apps/web`; it gains
   one allowed path: the GTM loader component under `apps/web/src/lib/consent/` plus the AdSense
   script in the article template, each covered by a test that asserts the default-denied consent
   state and the absence of health parameters.

**Alternatives.** (a) Keep "collects nothing" and measure with Play Console + Search Console +
Vercel's cookieless aggregate analytics (the pre-2026-10-28 plan; `04_GROWTH_PACK.md` §5.4):
cheapest, no banner, but no funnel, no Meta audience, no ads revenue. (b) AdMob in the app with
premium removing it: rejected as the default because the AdMob SDK collects device identifiers,
changes the Data safety form from "no data collected", invites Play's health-app review of an
ads SDK, and breaks the one sentence the wedge is built on. (c) A web paywall for premium
content: rejected, the static site has no accounts and would need a server, a database and a
payment processor the owner cannot use. (d) The old Payload CMS for content and SEO: rejected
again (ADR-072); the Markdown pipeline is the CMS, see `docs/34_GROWTH_OPS/00_GROWTH_OPS_PLAN.md`.

**Consequences.** A consent banner appears on the website for every visitor (not only the EEA;
one rule is simpler and Saudi PDPL also expects consent for non-essential cookies). The privacy
notice and the cookie line in `03_LEGAL_PACK.md` are rewritten (website section only). The
Play Data safety form is unchanged (the app still collects nothing). Lighthouse scores on content
pages will drop with ads; the budget in `04_GROWTH_PACK.md` §6.5 gets an "ads on" column.
Revenue, traffic and conversion numbers in `docs/34_GROWTH_OPS/02_MONETIZATION.md` are
hypotheses until the first month of real data. If the owner declines, alternative (a) stands and
the growth-ops plan runs without GA4, Meta or AdSense.

## ADR-076
**Date:** 2026-10-29 · **Status:** accepted 2026-10-29 (owner, in chat: "I need ads on both website and app … no health data (user health data) leaves app but ads are ok"; he does not believe readers will pay for premium features alone) · **Area:** app, privacy, revenue

**Context.** On 2026-10-29 the owner asked to "place the ads on website and mobile app". ADR-075
(accepted the day before) allows ads on the website after consent and keeps the app untouched:
no analytics, no ads, no network. Ads inside the app contradict that in four concrete ways, so
they are not wired without a decision of their own.

**The question.** Should the Android app show ads (Google AdMob, the only ads network that
works with Google Play Billing and an Egyptian seller), with femio Plus removing them?

**What "yes" costs, each one a fact of the SDK, not an opinion.**
1. **The INTERNET permission.** The AdMob SDK fetches ads over the network. The release manifest
   must request INTERNET, which the privacy tripwire forbids today and which the R6.9 spike was
   built to avoid (`testing-results/2026-10-29-play-billing-spike/`).
2. **The Data safety form changes.** AdMob collects device identifiers and approximate location
   for ads; the Play form moves from "no data collected" to "data collected and shared with
   third parties for advertising" (Google's own Data safety guidance for the SDK). The store
   listing, the privacy notice and the app-side consent screen (UMP / Google's User Messaging
   Platform) all change with it.
3. **Her record and the ad request share a process.** The record never leaves the phone, and the
   ads SDK never reads it; but "the app has no way to send anything" is a sentence the app can
   no longer say, and it is the sentence the wedge is built on (`docs/32_STUDY/00_SYNTHESIS.md`).
4. **Health-app review.** Play's health-apps declaration plus an ads SDK invites a closer review
   of a period-tracking app; the competitors that carry ads (Flo, the Arabic trackers) have
   compliance teams for it (`docs/34_GROWTH_OPS/reports/2026-10-28-competitor-monetization.md`).

**What "yes" buys.** Revenue from readers who never pay: at the benchmark's rates a health app
earns in the order of $1–3 per thousand ad impressions in Egypt and Saudi Arabia (benchmark
report §3, hypothesis until measured). "Premium removes the ads" becomes a real reason to buy,
which `02_MONETIZATION.md` §2 lists as the weakest part of the current Plus offer.

**Recommended default (what a session builds if the owner says nothing).** Decline for the
launch: the website carries the ads (R6.8 is built), the app stays sealed, and Plus is sold on
features, not on removing ads. Revisit after the first month of real revenue data from the
website, when the number in "what yes buys" is a measurement.

**Alternatives.** (a) Decline, as above. (b) Accept: AdMob with UMP consent, INTERNET permission,
new Data safety answers, the tripwire rewritten for the app, Plus removes ads; a release of its
own after the closed test, never in the first upload. (c) House ads only: the app shows its own
cards for femio Plus and the website guides, no SDK, no permission; this is already the plan
(`02_MONETIZATION.md` §2.3) and costs nothing to keep.

**Decision (2026-10-29).** Accept, with the line drawn where the owner drew it: **her health data
never leaves the phone; the ads SDK may.** Concretely (R6.13):
1. Google AdMob through `google_mobile_ads`, the only ads package; no mediation adapters, no
   analytics, no attribution SDK (the tripwire names them).
2. Banners on the guide screens only (`lib/domain/ads_policy.dart`: the Learn index and an
   article); never on Today, the log, the calendar, Help now, the warning signs, Settings,
   onboarding or the lock. A widget test asserts the absence on each of those screens.
3. Non-personalised ads everywhere, content rating capped at PG, the UMP consent form where
   Google requires it; the SDK receives no keywords, no content URL, no events, nothing about her.
4. INTERNET and ACCESS_NETWORK_STATE enter the merged manifest from the SDK alone. The tripwire
   now checks the thing that matters instead: no HTTP client, socket or WebSocket anywhere under
   `lib/`, the SDK imported only under `lib/features/ads/`, no personal permission (location,
   phone, contacts, camera, microphone) in the source or merged manifest.
5. The Data safety form says what the SDK sends (device identifiers, inferred approximate
   location, ad interactions, diagnostics: collected and shared for advertising), and nothing
   else; the privacy notice (EN/AR/FR/ES), the legal pack, the store listing and rule 4 of the
   constitution were rewritten the same day. "Ads: yes" in the Play forms.
6. femio Plus removes the ads: the first honest reason to pay, as the owner argued.
7. Ids (AdMob app id, unit ids) live in `apps/mobile/ads.env`, git-ignored, read at build time;
   without it a build shows Google's test ads.

**Consequences.** "The app has no way to send anything" is no longer true and is no longer said
anywhere; what is said, and checked, is "her records never leave the phone; the only thing that
does is the ad request, and it carries nothing about her". The Play review of a health app with an
ads SDK is the owner's accepted risk; the first upload carries the ads so the closed test exercises
them. Alternative (c), house cards for femio Plus, stays as the ad-free surface on every other screen.
